# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed

- **The transaction and account forms no longer squeeze two fields into a phone-width row.** ([Issue #145](https://github.com/aellington89/finance-stack/issues/145)) Date/Amount, Transaction Type/Category and, when editing an account, Opened/Closed Date sat in a fixed two-column grid. On a phone each field got about 140px, and the date ran across the Amount field. The rows now go two-up only once the form itself is 28rem wide, the narrowest width at which each half fits the longest date the picker shows. Below that they stack. The form's width decides, not the screen's: from `lg` up the Transactions page docks the form in a 380px column, so it stacks there too. That also stops the date running past its field on desktop ([Issue #321](https://github.com/aellington89/finance-stack/issues/321)).

  It is a container query (`@container` on each form, `@md:grid-cols-2` on its rows) rather than the `md:` breakpoint the issue proposed, because a viewport breakpoint cannot see that column. `md:` would have kept the docked form two-up at 348px, where each half is 166px and 228 of 2026's 365 dates overrun it; the widest, "September 22nd, 2026", needs a 204px button. The account form is 512px wide on desktop, so it stays two-up there.

## [1.1.1] - 2026-09-25

**Migration:** none

### Fixed

- **The Debt and Net Worth waterfalls drew a period's movement as slivers.** ([Issue #251](https://github.com/aellington89/finance-stack/issues/251)) Both charts drew Start and End as bars rising from $0, so the Y-axis had to span the whole balance. The bars between them, which are the reason to draw a waterfall, came out 1–2% tall. On a $250K debt moved by a few thousand dollars, Payments, Interest and Other barely registered. The axis now zooms to the bridge and cuts Start and End off at the edge of the plot.

  It zooms only when that at least doubles the scale of the bars, measured on the axis as it will actually be drawn. A bridge that crosses $0, or that is already big enough to read, keeps the $0-based axis exactly as before. The zoomed range covers every level the bridge passes through, not just its two ends, because payments can lift the running balance well past both before interest and other changes bring it back. Tick values are round, and the step is never finer than the compact `$…K` labels can tell apart, so no label repeats.

  A plain `domain` could not have done this. recharts stacks every bar from 0 and widens any domain back out to include it, so the zoom needs `allowDataOverflow`, which is also what clips Start and End. Only the axis changed. The bars are the same, so `start + payments + interest + other = end` still reconciles, and the tooltip and the empty state are unchanged. The logic is in the unit-tested `waterfall-axis.ts`, next to the bar builders; each chart gained only three `YAxis` props.

## [1.1.0] - 2026-09-23

**Migration:** backward-compatible

### Changed

- **The coverage denominator grew 62% and the number held: 1649 → 2677 statements, 88.3% → 86.1%.** ([Issue #296](https://github.com/aellington89/finance-stack/issues/296)) Removing the blanket `**/*.tsx` exclusion added the React tree to a map that had never contained it. The global thresholds move only 85/75/83/86 → 84/73/77/84, which is the result worth reporting: the old figure was high partly because it was not asking the components anything, and the new one is over a set that includes them. `lib/**/*.ts` and `scripts/**/*.ts` are untouched by this issue and still hold at their #142 values. The gate was verified to still bite — deleting one render test fails the run on four separate `components/**/*.tsx` assertions.

  **Eighteen copies of four functions became one each.** `formatCurrency` was defined identically in six dashboard components and eleven chart components (there as `formatCurrencyFull`) plus privately in `lib/format/financial.ts`; `formatCurrencyCompact` had ten copies, `formatDate` four and `parseDate` two — thirty-three definitions of four functions, none able to drift visibly because they were byte-identical, and all of which would have had to be found and edited together if a format ever changed. They now live in `lib/format/financial.ts` and a new `lib/format/dates.ts`, both tested. `parseChartDate` is the one worth naming: the `T00:00:00` it appends is what keeps a `YYYY-MM-DD` column from being parsed as UTC midnight and rendering as the previous day for every viewer west of Greenwich.

  **The chart files were emptied before they were excluded, and the order is the whole argument.** Eleven grouping arms of axis formatting (`makeTickFormatter` / `makeTooltipLabelFormatter`, previously unreachable by any test) moved to `accounting-axis.ts`; two byte-identical `pivotByCategory` copies and `pivotDecomposition` collapsed into one generic `timeseries-pivot.ts`; the bar builders and `getBarColor` had already gone to `*-bars.ts`. Excluding the wrappers first would have hidden real, untested code behind a plausible reason.

  **Five pure transforms moved out of `.tsx` components into `.ts` siblings, which is what made their existing coverage count.** `buildDebtMixTiles`, `buildLiquidityTiles`, `buildWaterfallBars` and `buildDebtWaterfallBars` now live in `debt-mix-tiles.ts`, `liquidity-tiles.ts`, `waterfall-bars.ts` and `debt-waterfall-bars.ts`; `formatPercentChange` moved into `lib/format/financial.ts` beside the `signedPercent` it wraps. Their tests already ran and already gated behaviour — they were simply invisible to the report, because the functions were exported *from* files the denominator excluded. Not one assertion in those five files changed, which is the evidence the move was mechanical. `components/**/*.ts` consequently went from two incidental helpers to seven modules and its threshold from 78/85/82/78 to 97/96/98/97. Three previously-private functions came along and gained first tests: both copies of `getBarColor`, and `chartColorVars`, whose key filter is the security half of [#237](https://github.com/aellington89/finance-stack/issues/237).

  **`components/**/*.ts` rose from 78/85/82/78 to 97/94/98/97**, because the glob that used to cover two incidental helpers now covers nine modules, every one of them logic lifted out of a component. `components/**/*.tsx` is gated at 74/63/66/76 against a measured 77/65/69/79 — which is #142's deferred "~70% for components" acceptance criterion, met rather than deferred again.

  **`components/ui/**/*.tsx` is excluded, on different grounds than `**/*.tsx` was.** The old reason was that the suite could not reach those files; it now can. The new reason is that all 24 are generated by `npx shadcn add`, which rewrites them wholesale — so gating them would turn a routine re-generation into a CI failure with no bug behind it. They still execute, inside the components that *are* gated. Extracting `chartColorVars` into `ui/chart-colors.ts` is what kept the one security-relevant function in that directory inside the denominator, and it has the side benefit of moving it out of the file `ui/chart.tsx` warns will be clobbered.

  **A correction to the config's own documentation, found while doing this: vitest 5 changed how `coverage.include` matches.** Under vitest 4 it was applied with picomatch's `contains: true`, matching a pattern against any *substring* of the absolute path — so `components/**/*.ts` also matched `card.tsx`, and the blanket `**/*.tsx` exclusion was genuinely the only thing holding the React tree out of the report. That was documented as "trap 2" in both `vitest.config.ts` and `docs/testing.md`, and it is no longer true: vitest 5 globs are anchored. Removing the exclusion on its own moved the denominator by 11 statements, and the 41 component files appeared only once `components/**/*.tsx` was added to `include` explicitly. The same release emptied `coverageConfigDefaults.exclude` — it used to carry `**/node_modules/**` and `**/[.]**` — so the note about spreading the defaults is now vestigial, and what actually keeps `node_modules` and `.next/standalone` (which contains a full second copy of `components/`) out of the map is that every `include` glob is anchored. Both documents now say the current rule and what it replaced, because the old behaviour is the one a reader will have in mind.

- **The importer resolves primary keys by name instead of by hardcoded id, and refuses to run a parser whose rows are missing.** ([Issue #273](https://github.com/aellington89/finance-stack/issues/273)) `poll.py` has always built name → id maps for `accounts`, `transaction_categories` and `transaction_types` and handed them to every parser. The paystub parser discarded them — `del lookup_maps` — and pinned seventeen primary keys as integer literals instead, twelve of them `transaction_category_id` values and one an `account_id`. Those thirteen rows are the user's: they ship nowhere, and `/settings/categories` offers them for rename and delete like any other row. Under the seed-data taxonomy in [docs/database.md](docs/database.md#seed-data-taxonomy) that is the cell the document calls a defect rather than a category, and it was its second instance — [#109](https://github.com/aellington89/finance-stack/issues/109) fixed the neighbouring one and left this explicitly out of scope.

  **The dangerous case was never the delete.** Deleting a pinned category makes the next import fail on a foreign key, which is loud and fine. Deleting it and letting the id be *reused* filed federal income tax under whatever category then occupied that id — no error, no way to notice, and wrong in the data from then on. Resolving by name cannot do that: a reordered, renumbered or reused id resolves to nothing rather than to the wrong thing.

  **The reason the maps were discarded was real, and is now fixed rather than worked around.** They carried no `account_identifier`, which the net-pay distribution matcher needs to resolve a masked `xxxxxx3401` against an account — so the parser queried `accounts` directly and, having opened that door, hardcoded twelve category ids the maps already covered. `load_lookup_maps()` now carries `account_identifiers` too, and a new tracked `importer/lookups.py` holds the resolution itself: `resolve`, `resolve_all` and `resolve_account_by_last4`, all pure functions over the maps, all raising a shared `MappingError` that names the row that is missing and what needed it.

  **Names are not unique either, and pretending otherwise would have replaced one silent wrong answer with another.** None of `account_name`, `transaction_category` or `transaction_type` carries a `UNIQUE` constraint, so two rows can share a name and the name → id dict kept only whichever Postgres read last. `load_lookup_maps()` now records every such collision and warns about it at load time, and `resolve()` refuses an ambiguous name outright. The same applied to the last four digits of an `account_identifier`: the old matcher built `{last4: account}` and let the last row win, so a replaced card could silently redirect a distribution. It now raises, naming every candidate and marking the closed ones.

  **An `account_identifier` is not unique, and storing it as though it were had already gone wrong.** `account_identifiers` maps each identifier to a *tuple* of account ids, because a credit union keeps one member number against the checking, savings and loan rows alike — a bare `{identifier: account_id}` collapses them and hides the collision. That is what the old matcher did, and in March 2026 the row it happened to keep stopped being the checking account, so six months of one recurring net-pay distribution posted to a HELOC instead. No error was possible: the destination was a real account and the foreign key was satisfied. Where the identifiers are genuinely identical no query can break the tie, so the parser now disambiguates on the account type the paystub prints beside the masked number and resolves the result by name.

  **A parser may declare `REQUIRED_LOOKUPS`, and the dispatcher proves it before opening a document.** This is the gate, and it is a runtime one because it cannot be anything else: `importer/parsers/` is gitignored, so no assertion in this repository can see which rows a parser depends on — there is nothing for a `findFixtureGaps`-style check to read, which is why this gap had no way of being noticed in the first place. A missing row is one error naming *every* absent name, and the type's files are skipped with nothing recorded against them, so creating or renaming the rows lifts it on the next poll. That also catches what no fixture gate could: a row deleted in production.

  **A first miss no longer means a restart.** The maps load once per connection, so a category created in `/settings/categories` minutes ago is not in them and a miss proves nothing. Both the preflight and a `MappingError` raised from `process()` now trigger one map reload per sweep and one retry, then give up — so a genuinely missing row still fails loudly and a permanently bad file is not re-parsed forever.

  Categories 16 to 20 and account 27 are consequently **no longer referenced by anything**, so they are not added to `finances-test-mock-data.sql`: shipping one person's benefits elections and employer to every install is the objection that rejected shipping the liability rows in [#111](https://github.com/aellington89/finance-stack/issues/111), and it applies unchanged here. Going the whole way to a `payroll_*` `reporting_role` domain was considered and rejected for the same reason — a role answers *which categories are in this bucket*, while a parser needs a 1:1 map from one document label to one category, so it would take twelve roles to say what twelve names already say. A rename still breaks resolution; that residual coupling is recorded in the taxonomy rather than hidden.

- **The release-notes generator can suggest a major, and the changelog gate refuses a breaking release that is not one.** ([Issue #315](https://github.com/aellington89/finance-stack/issues/315)) `suggestBump()` could only ever return `minor` or `patch`, and its comment still claimed pre-1.0 `0.MINOR.PATCH` versioning — an assumption that went stale at `v1.0.0`. The arithmetic was never wrong; the *coverage* was. Post-1.0 a breaking change is a major, and the generator had no path to say so: it would have proposed `1.0.1` for a release that ought to be `2.0.0`, on exactly the release where the version number carries the most information. Nothing downstream caught it either, because the changelog gate compares `package.json`, the newest `CHANGELOG.md` heading and the pushed tag against *each other* — they would have agreed, on the wrong number.

  **The signal was already in the file.** The issue assumed the `**Migration:**` marker is written after the bump is suggested, which is true only of a closed release heading. `## [Unreleased]` carries one the whole time: every PR that ships a migration sets or escalates it as it lands, so it is sitting there when `npm run release:notes` runs. The generator now reads it and a `breaking` marker suggests a major — no new label, no new convention, and nothing for a drafter to remember.

  **The marker only sees the database, so it is not the whole answer.** It says whether an operator can roll back by re-pinning the previous image; it says nothing about a removed environment variable or a changed deployment contract, either of which is a major that ships `**Migration:** none`. A new `--bump=major|minor|patch` flag is the way to say so, and it lowers as well as raises for a marker that overstates the impact. The value attaches with `=` because the range is parsed as the first non-`--` argument — a space-separated `--bump major` would silently have become the git range, so it is rejected outright, as is an unrecognized or mis-cased value. Post-1.0 the drafted block also carries a comment naming the gap, because a tool that can only see half the question should say which half.

  **The gate is the half that actually enforces it.** A suggestion is advisory — it is pasted into a heading a human then confirms — so the generator alone could not close the issue. `check-changelog` now also asserts that a release declaring `**Migration:** breaking` incremented its major over the previous release, which fails on every push and again on the tag push before any image is built. A major that declares `none` is still fine (`v1.0.0` was exactly that), a breaking release that skips a major is legal semver and is left alone, and pre-1.0 releases are exempt, where a breaking change legitimately shipped as a minor. No release in this changelog declares `breaking`, so the gate was green the day it landed.

  The pre-1.0 branch is unreachable now and is kept deliberately: its six original tests were left byte-identical, which is the only evidence that giving the generator a major path changed nothing about how the fourteen releases below this one were numbered.

- **`components/ui/chart.tsx` no longer injects a stylesheet, and `ChartConfig` no longer accepts per-theme colours.** ([Issue #237](https://github.com/aellington89/finance-stack/issues/237)) Upstream shadcn emits a `<style>` element through `dangerouslySetInnerHTML` — the only one in this app — carrying each chart's `--color-*` declarations twice, once plain and once under `.dark`. The container sets them as a plain `style` object instead. Custom properties inherit, so they still reach every recharts element inside the SVG, which is all the injected stylesheet was ever achieving.

  **The `theme: { light, dark }` variant is gone from the type rather than left unused.** No config in this app ever set one — all ten pass a single `color`, which made the `.dark` half of the generated CSS a byte-identical duplicate of the light half — and a `style` attribute cannot express two theme scopes. Keeping the type would have meant accepting a per-theme colour at compile time and dropping half of it at runtime. This diverges from upstream, so `npx shadcn add chart` will clobber it; the file says so at the top.

  **The reason to do this at all was the injection sink, not the CSP.** `style-src` still allows inline style, so this unblocked nothing. But `expenses-category-chart.tsx` builds its config keys from *database category names*, and upstream drops them unescaped into a `<style>` body — where a `}` closes the rule and whatever follows becomes new selectors. A style attribute is a far smaller surface, and keys that are not valid CSS identifiers are now refused outright rather than emitted as dead declarations. Worth knowing when reading the diff: nothing in a production build resolves these variables through `var()` — all nine dashboard charts hand colours straight to recharts, and `/test-ui`, which does resolve them, calls `notFound()` outside development. That is why `e2e/csp.spec.ts` reads one back out of `getComputedStyle` rather than trusting the dashboard to look right.

### Added

- **A third vitest project mounts React, so components and hooks are measured for the first time.** ([Issue #296](https://github.com/aellington89/finance-stack/issues/296)) [#142](https://github.com/aellington89/finance-stack/issues/142) set coverage thresholds and, to keep them honest, first had to decide what the percentage divides by. It excluded `**/*.tsx` outright, because nothing in the suite could render a React tree: both projects were `environment: node` and collected `*.test.ts` only, so a component could be imported but never mounted. That left #142's second acceptance criterion — "~70% for components" — deferred rather than met, with 65 of the 67 files under `app/components/` outside the denominator. A `jsdom` project now collects `tests/unit/**/*.test.tsx`, and twenty-four render tests take `components/**/*.tsx` from unmeasured to **77%** — every component file but `app-sidebar.tsx`.

  **Split by file extension, not by directory.** Both the `unit` and `jsdom` projects collect from `tests/unit/`; the globs are `*.test.ts` and `*.test.tsx`, which are disjoint by construction, so no file can be picked up by two projects and a component test lives beside the transform test for the same feature. Four devDependencies (`jsdom`, `@testing-library/react`, `@testing-library/jest-dom`, `@testing-library/user-event`) and deliberately **no** `@vitejs/plugin-react` — `tsconfig.json` already sets `"jsx": "react-jsx"`, so Vite's esbuild transforms `.tsx` unaided and the plugin would add only Fast Refresh, which tests do not use.

  **`afterEach(cleanup)` is explicit, and that is the one thing to know before writing the twelfth test.** Testing Library registers its own cleanup through the global `afterEach` only under `globals: true`, and this suite imports `describe`/`it`/`expect` from `"vitest"` instead. Without the explicit call the previous test's tree stays mounted and the *second* render of a component in any one file starts failing with "found multiple elements" — which reads as a bad selector rather than as a missing teardown. The setup file also stubs `window.matchMedia` and `ResizeObserver`, neither of which jsdom implements and both of which are reached on mount rather than on interaction, so a render throws before a single assertion runs.

  **The eleven recharts wrappers are excluded, and the reason is a measurement rather than a reputation.** The first answer here was "recharts under jsdom is brittle", which is the received wisdom and was not checked. It mounts fine. What it does not do is *render*: `ResponsiveContainer` has no layout under jsdom, so a mounted chart produces `{svg: 0, rect: 0, text: 0}` — the container element and nothing inside it. A render test consequently buys 41% of the file's statements, 2 of its 8 functions and 0% of its branches, while asserting only the card title, and every tick and tooltip formatter stays unexecuted because no axis is ever drawn. That is a number going up with nothing verified, so the files leave the denominator instead. The `-chart.tsx` suffix in the exclusion is load-bearing: it keeps `gauge-badge.tsx`, the one hand-rolled SVG in that directory, *in* the denominator, where it renders fully and is tested.

  **Anything reaching `next-auth` cannot be mounted at all**: it fails to resolve under vitest's jsdom environment with `Cannot find module 'next/server'`, so a component whose children import a server action cuts the chain with a `vi.mock` of the action module.

  `hooks/**` came in at the same time, and the shape of that change is worth recording: the old `hooks/**` *exclusion* was belt-and-braces, because no `include` glob had ever reached the directory. Measuring it meant **adding** `hooks/**/*.ts` to `include`, not deleting an exclude entry — a distinction that is invisible in the issue and cost a wrong first attempt.

- **A self-hosted GlitchTip ships behind `--profile errors`, so error history stays on the host.** ([Issue #232](https://github.com/aellington89/finance-stack/issues/232)) The backend for the DSN above. Off by default, like the `bi` and `edge` profiles, and the stack is byte-identically unchanged until it is started. It closes the durability half of the issue: before it, error history lived only in Docker's `json-file` ring buffer, capped at 3 × 10 MB per service and present in no backup, so the record of a failure outlived the failure by about a day on a busy stack.

  **One container, not the three a Sentry-compatible backend usually implies.** `SERVER_ROLE=all_in_one` runs the web process, the embedded worker and its own Django migrations together, and `VALKEY_URL=""` moves the task queue, cache and session storage onto Postgres. The second setting was chosen for more than the saved container: `lib/security/rate-limit.ts` and `docs/deployment.md` both state there is no Redis in this stack, and the in-process rate limiter is justified partly on that premise. Introducing one here would have reopened that argument silently, in a file nobody reviewing error tracking would think to read.

  **Its database rides the existing Postgres, owned by a role that can reach nothing else.** `init-db/roles/04-glitchtip-role.sql` is a deliberate near-copy of the Metabase convergence file, including its statement order — own the database, revoke PUBLIC, grant what the startup migrations need, strip cluster attributes last — because both roles are the same shape: a third-party web application that migrates its own schema at boot and must hold nothing on the cluster. Where the two files differ, the difference is a bug in one of them. `assert-grants.sql` needed no change to cover the new role, which was the design goal rather than a happy accident: its sweep already fails any undeclared login role that gains `CONNECT` on `Finances`, so a role confined to its own database passes exactly as `metabase_user` does, and one widened out-of-band does not. `scripts/verify-db-roles.sh` gains the behavioural half — it connects as the role, proves it can create and drop a table in its own database, and proves it is refused on `Finances`. An empty `GLITCHTIP_DB_PASSWORD` skips provisioning entirely, the same way an empty `MB_DB_PASS` skips Metabase.

  **Alerting is still not configured, and the documentation says so rather than implying otherwise.** GlitchTip notifies by email only — no webhook, Slack or Discord — and the shipped `EMAIL_URL` is `consolemail://`, which writes notification mail to its own container log. So this closes the issue's durability gap and leaves its alerting gap open: an alert is a log line, in a different container. Setting `GLITCHTIP_EMAIL_URL` to a real relay closes it, and that is opt-in because the alternative is an SMTP credential and an outbound mail dependency on a stack the README says to keep on a trusted network.

  Smaller decisions, recorded because each was a choice: it binds `127.0.0.1:8000` only, on the #130 reasoning that applies to Metabase — it holds every captured error message and has no business on the LAN. Self-signup is closed by default, because on a trusted network open registration means anyone who can reach the port can create an account; the first user comes from `./manage.py createsuperuser`. `ALLOWED_HOSTS` is set rather than left at its wildcard default, which the container warns about on every start. The healthcheck probes `/_health/` with `python`, not `curl` or `wget`, because the image ships neither. And the `glitchtip` database is in the default `BACKUP_DBS` — safe to add unconditionally because `backup.sh` already skips a database that does not exist, a path metabase has exercised since it was written.

  One consequence worth stating for whoever bumps the pin next: `deploy/compose.yml` carries the same `glitchtip/glitchtip` tag, and Dependabot still only watches the repository root, so an image bump will update one file and fail the parity gate until [#304](https://github.com/aellington89/finance-stack/issues/304) lands. The gate itself was taught about the new profile — `check-deploy-parity.sh` renders with `--profile errors` now, without which it would have compared the two files while silently ignoring the service they disagreed about.

- **`reportError()` has a second sink: any backend speaking the Sentry ingest protocol, behind one optional variable.** ([Issue #232](https://github.com/aellington89/finance-stack/issues/232)) [#129](https://github.com/aellington89/finance-stack/issues/129) built the capture seam and deliberately shipped no backend, which left error history as a rolling window — Docker's `json-file` driver keeps 3 × 10 MB per service and rotates the rest away, and none of it is in the `pg-backup` set. Setting `ERROR_DSN` now also ships each failure to GlitchTip, Sentry SaaS, or anything else speaking the same protocol. Unset is a supported configuration and the default: the structured logger stays the only sink, no outbound request is made, and nothing else about the stack changes.

  **No SDK ships, and the reason is the redaction rather than the dependency count.** The obvious change — `Sentry.captureException(error)` beside the log call — hands the SDK the *raw* error, which still carries `DrizzleQueryError.params`, every bound value of the failing statement, and pg's `detail`. It would ship the row that [#129](https://github.com/aellington89/finance-stack/issues/129)'s redaction exists to strip, and every rule in `serializeError()` would become decorative. An SDK can be told to behave with a `beforeSend` hook, but that is a second copy of the rules, free to drift from the first. `reportError()` instead runs `serializeError()` once and hands the result to both sinks, and the new `lib/error-tracking.ts` takes `LogFields` rather than `unknown` — so the leak is unreachable rather than guarded against. Keeping that property is a stated constraint on the module: nothing in the capture path may accept a raw error.

  **The dependency argument is secondary but decided where it landed.** `@sentry/nextjs` pulls the OpenTelemetry package set into *production* dependencies, and both `npm audit` gates block on HIGH with no per-advisory allowlist — a HIGH anywhere in that tree is a red gate with no escape hatch, unlike a Trivy finding. The same tree becomes scannable surface in two images, and the SDK would additionally need a `register()` export `instrumentation.ts` does not have, `withSentryConfig` around `next.config.ts`, and a `SENTRY_AUTH_TOKEN` build secret that [docs/secrets.md](docs/secrets.md) forbids by rule. What the hand-rolled transport gives up is breadcrumbs, source-mapped frames and automatic instrumentation; stack traces are sent as a string rather than parsed frames, so they read but do not click.

  **Capture is server-side only, and that falls out rather than being enforced.** `ERROR_DSN` has no `NEXT_PUBLIC_` prefix, so Next never inlines it and the value is simply `undefined` in a client bundle — the same mechanism `log.ts` already relies on for `LOG_LEVEL`. Both client error boundaries reach the transport and return without doing anything, with no runtime check, and CSP's `connect-src 'self'` needs no exception. The alternative would have baked one operator's DSN into every published image. The ceiling it buys is small and now documented: a genuine browser-side throw stays console-only, while Server Component errors are unaffected, since React redacts those to a bare digest before they cross the wire and `instrumentation.ts` captures the real one under the same digest.

  **Delivery cannot make an incident worse.** Sends are fire-and-forget so `reportError()` stays synchronous and `void` for its call sites, two of which are inside a React `useEffect`; nothing in the path may throw over the top of the error being reported. A 2-second timeout bounds a stalled ingest host, and after five consecutive failures a breaker opens for a minute, so a backend that is down does not turn every application error into an outbound request that also fails. It logs once on opening and once on recovery rather than once per dropped event, at `warn` and not `error` — routing a capture failure back through `reportError()` would recurse.

  Redaction is now asserted twice over: once against the emitted log line and once against the captured request body, in both `tests/unit/lib/report.test.ts` and `tests/integration/actions/logging.test.ts`, the latter still driving a real foreign-key violation through `createAccount` so the model cannot drift from what the driver throws. `docs/observability.md` also gains the fifth capture point it had been missing — `api/health/seed-data/route.ts` — which its "three capture points" table never listed.

- **The importer no longer re-imports a file it has already imported, and a single bad file no longer takes the service down with it.** ([Issue #124](https://github.com/aellington89/finance-stack/issues/124)) `importer/poll.py` had no notion of what it had already done: it re-read the whole drop folder on every 60-second poll, and the only thing standing between a re-dropped statement and a duplicate set of transactions was a hand-written guard inside one parser — which every *new* parser would have had to remember to write for itself. Worse, the dispatcher answered every parser exception with `sys.exit(1)`, and `restart: unless-stopped` then brought the container straight back onto the same file. One malformed PDF meant a permanent crash loop, and every other file queued behind it was never imported at all.

  Every file is now hashed and recorded in a new **`import_log`** table (migration `0007_add_import_log.sql`). Bytes that already carry an `imported` row are skipped without the parser ever being called, so re-dropping a file under any name is a no-op; a parser exception writes a `failed` row with the error text and the loop moves to the next file. Parsers no longer need duplicate guards of their own, and `process()` may now optionally return the number of rows it inserted, which is recorded as `row_count` — an optional return rather than a signature change, because `importer/parsers/` is gitignored and user-maintained, so a breaking contract change would land in working trees this repository cannot see.

  **On the first poll after this upgrade, anything already sitting in `imports/` is handed to its parser once more**, because `import_log` starts empty and nothing recorded those files at the time they were imported. The existing parsers' own duplicate guards absorb it — that re-parse inserts nothing and is recorded as an import of zero rows — so the practical effect is one quiet sweep. A parser written without such a guard would duplicate its rows, though, so empty its drop folder first if you have one. Every later poll is covered by the hash.

  **The quarantine is a row, not a `imports/.failed/` directory**, which is a deliberate departure from the issue as filed. The importer runs as uid 1001 against a host-owned drop folder and [`importer/Dockerfile`](importer/Dockerfile) rests its non-root design on the service writing nothing to disk, so moving files would have meant reworking the ownership of the folder holding the user's own documents. It would also have worked against where this is going: `finance_app` already holds `SELECT` and `INSERT` on every table by default privilege, so a review UI can query `import_log` on day one, whereas a `.failed/` directory would be invisible to a container that mounts no `./imports` at all — and would introduce a second source of truth that can disagree with the first. Because the key is content, fixing the file lifts the quarantine by itself; restarting the importer also retries everything quarantined, on the assumption that a restart is what fixing a *parser* looks like.

  **The guarantee lives in a partial unique index on `(sha256) WHERE status = 'imported'`, not in the lookup.** Checking before inserting is check-then-act and races with itself; the index makes a second successful import of identical bytes impossible regardless, and is partial precisely so that repeated failures of the same file can still accumulate. `import_log` is append-only for the same reason `transactions` is — `finance_importer` gains `SELECT, INSERT` and no new verb, so the role's standing promise that a bad parser can only ever add rows now covers the record of what it did as well. `scripts/verify-db-roles.sh` asserts the `UPDATE` and `DELETE` denials so that widening the grant later cannot pass CI quietly.

  **Two orderings in the new code are load-bearing and invisible in a passing run**, so both are pinned by tests that were confirmed to fail without them. The success row is written *inside* the parser's transaction, so the rows and the record that they landed commit together; the failure row is written *after* the rollback, in a transaction of its own, because recording it first would roll it away with the parser's work and leave the file retried on every poll forever. Separately, connection-level failures are classified apart from parser failures and quarantine nothing — without that split a routine Postgres restart would have dead-lettered every good file in the folder, which is a considerably worse failure than the crash loop being fixed. Those cycles now back off exponentially from `POLL_INTERVAL` to a 15-minute ceiling instead of exiting.

- **The importer has tests, and CI runs them.** ([Issue #124](https://github.com/aellington89/finance-stack/issues/124)) `importer/tests/` is the repository's first Python suite — until now the one non-Node component had no automated coverage of any kind, and CI touched it only to build its image. `test_poll.py` covers the dispatch loop against fakes and needs nothing; `test_import_log.py` covers the CHECK constraints, the partial unique index and the importer's privileges against a real database, and skips rather than fails when `IMPORTER_DATABASE_URL` is unset. It runs as a step in the existing `ci` job rather than a job of its own, because that job has already stood up Postgres, applied the migrations and created the roles — which also makes the integration half a live check that [`init-db/roles/02-grants.sql`](init-db/roles/02-grants.sql) was really applied. It connects as `finance_importer` rather than as the superuser on purpose: the append-only guarantee is a privilege, and a suite running as a role that cannot fail the assertion would be proving nothing.

  Note that the real parser cannot be a fixture — `importer/parsers/` is gitignored, so it is absent in CI and on any fresh clone — and the suite therefore runs entirely against a `FakeParser`. Python is excluded from the Vitest coverage thresholds; the two suites share a job, not a denominator.

### Fixed

- **The release-notes generator drafted this very section as a patch.** `npm run release:notes` proposed `1.0.5` for an `[Unreleased]` holding three features and a migration, and two independent gaps produced it. It only ever read labels off `Issue #N - ` commits, so a PR squashed under a freeform title — `Nonce-based CSP: … (#237) (#333)`, labelled `enhancement` on both the issue and the PR — reached it unlabelled; and the two features it could see were labelled `bug` ([#124](https://github.com/aellington89/finance-stack/issues/124)) and `infrastructure,backend` ([#232](https://github.com/aellington89/finance-stack/issues/232)), so no `enhancement` label existed to find.

A `breaking` marker and `--bump=` still outrank it. A `backward-compatible` marker is deliberately not a minor signal by itself: an index-only migration can ship in a fix, and it still rolls back by re-pinning the image. Run against this section, the generator now suggests `1.1.0`.

### Security

- **The CSP is nonce-based: `script-src` no longer allows inline script.** ([Issue #237](https://github.com/aellington89/finance-stack/issues/237)) [#182](https://github.com/aellington89/finance-stack/issues/182) shipped the policy with `'unsafe-inline'` on `script-src` and `style-src` and said so plainly, because the alternative was a nonce and the nonce needed this work. `'unsafe-inline'` on `script-src` is the whole difference between a policy that stops injected script *running* and one that only stops it *phoning home*: the tight directives around it — `default-src`/`connect-src 'self'`, `form-action`, `base-uri`, `object-src 'none'` — were always doing the second job well and could never do the first. `proxy.ts` now mints 128 bits of CSPRNG per request and sets the policy on both the response and the forwarded request headers; Next reads the latter and stamps the nonce onto its own bootstrap and flight-data scripts, and the root layout hands it to `next-themes` for the script that sets the theme before first paint.

  **The policy is emitted from two places now, and which one wins is load-bearing.** `next.config.ts` cannot mint a per-request value, so it compiles a nonce-free *floor* into the routes-manifest and `proxy.ts` overwrites it on everything that can carry HTML. That the second overwrites the first rather than joining it was verified rather than assumed — Next builds its route list with the manifest headers ahead of the proxy and both assign into one map — and it matters more than it sounds: a browser enforces every policy it is sent, so two headers would have intersected into something nobody wrote. The floor omits `'unsafe-inline'` too, although nothing it covers runs an inline script, so that the arrangement fails closed: if the overwrite ever stops happening the app fails to hydrate visibly, instead of quietly serving a weaker policy that still looks correct to `curl -I`.

  **Every route is rendered per request as a consequence, and that is the point rather than the price.** Reading the nonce in the root layout opts the whole app into dynamic rendering. It has to: a prerendered page's inline scripts are baked in at build time carrying no nonce, so serving one under this policy means it never hydrates. Only `/` and the 404 page actually changed — the fourteen dashboard pages already exported `force-dynamic`, and `/login` was already dynamic because it awaits `searchParams`, which the issue had not noticed.

  **Development deliberately gets no nonce.** CSP3 has browsers ignore `'unsafe-inline'` outright once a nonce is present, so minting one in dev would not widen the policy, it would silently drop the fallback that Turbopack's HMR runtime and error overlay depend on. `next dev` serves the floor unchanged. The nonce path is covered instead by a new `e2e/csp.spec.ts`, which runs against the production build — the only build where the nonce exists at all, which makes a dev-server run of that spec worse than no spec.

  **`style-src` keeps `'unsafe-inline'`, and that is upstream's constraint rather than a deferral.** Two things inject a `<style>` element with no nonce and no way to accept one: `sonner`, which builds the whole of a toast's styling in JavaScript — 109 rules, `position: fixed` among them, and nothing else styles a toast, so a nonce there turns every save and delete confirmation in the app into unstyled text in the document flow; and Next itself, in the 404 fallback it renders from `http-access-fallback/error-fallback.js`. The original issue named `next-themes` and `components/ui/chart.tsx` as the two blockers and expected both directives to close together; `next-themes` takes a `nonce` prop for both its script and its transition suppressor, `chart.tsx` was fixed below, and neither was ever the thing standing in the way of `style-src`. The unit test asserts the `'unsafe-inline'` that remains, for the same reason the old one asserted the `script-src` half: so that removing it is a deliberate change with a failing test attached.

  **`auth.ts` lost its `authorized` callback, which had to go rather than merely stop being called.** Passing a function to `auth()` does not bypass that callback — `handleAuth` still invokes it and then discards the result, because the branch that acts on it is only reached when no middleware function was supplied. Left in place it would have read as the gate while gating nothing. The redirect it used to drive now lives in `proxy.ts`, over the same four page trees and producing the same `callbackUrl`, and it carries the security headers that a proxy-generated redirect previously missed.

  The proxy's matcher widened from those four trees to everything except `/_next/static`, `/_next/image`, `/favicon.ico` and `/api/health`. The last exclusion is the deliberate one: matching it would have made the Docker healthcheck and the release smoke test depend on Auth.js decoding a session, a coupling that did not exist before and has no reason to start.

## [0.4.1] - 2026-08-29

**Migration:** none

### Added

- **The core money path is now tested end to end, in a browser, against the build that ships.** Every piece of it was already covered and the *wiring between the pieces* was not: `tests/integration/actions/transaction.test.ts` calls `submitTransaction()` with a hand-built `FormData` and a mocked session, and `tests/integration/queries/rebuild-balance.test.ts` checks the rebuild SQL — so a renamed form field, a page that stopped revalidating, a proxy redirect, or a KPI reading the wrong point of the series could all reach `master` with a green suite. One Playwright spec (`app/e2e/money-path.spec.ts`) now signs in, creates an account with an opening balance, posts a transaction against it, and asserts the dashboard Net Worth headline moved by **exactly** the amount posted. It runs as its own `e2e` job in `ci.yml`, for the same reason the `image` job is separate: it needs a Next build and a browser download the database gates have no use for, and a failure should read as "the money path broke" rather than as one more red step among fifteen.

  **It is a delta assertion, and that is what makes it a gate rather than a snapshot.** `init-db/seeds/finances-test-mock-data.sql` generates twelve months relative to `CURRENT_DATE`, so Net Worth has no fixed value to assert against; the spec reads the headline before and after and compares the difference. The alternative — a near-empty database with an exact expected total — was rejected because `shared-lookups.sql` ships no `account_types` at all (they come from the mock-data seed), so it would have meant a **third** seed file to keep in step with the other two. For the same reason the suite runs against `Finances_Test` rather than a database of its own: that database already *is* "a fixture seeded from `init-db/`", and a second provisioning path would drift from `app/scripts/migrate-and-seed.sh`, which hardcodes it. The guard that refuses to run against anything but the test database moved out of `tests/integration/setup.ts` into `tests/support/assert-test-database.ts` so both suites make one assertion rather than a copy each. Two details in the spec are load-bearing and easy to get wrong when extending it: the account type must sit in a non-restricted category, because `getCurrentNetWorth()` excludes Restricted Asset from Net Worth and a restricted type would make the delta zero and the assertion vacuous; and Opened Date is left blank so the opening-balance transaction is dated today, which is what puts a balance row at `CURRENT_DATE`.

  **The gate was proven to fail before it was trusted**, and the recipe is in [`docs/testing.md`](docs/testing.md#end-to-end-tests) rather than in a reviewer's memory: comment out the `rebuildAccountBalance()` call inside `submitTransaction`, and the last step reports the KPI standing still. Deliberately *not* automated as a CI negative check in the shape of the [#239](https://github.com/aellington89/finance-stack/issues/239) attribute gate — that pattern earns its cost when the property is invisible in a passing run, and here it would roughly double E2E wall-clock on every PR to re-prove something a one-line local mutation demonstrates. The suite runs the **production** build on port **3100**: `next dev` compiles a route on first hit, which is slower and flakier, and its CSP is not the shipped one; 3001 is bound by both the `start` script and the `finance-app` container, so a suite there would either fight the running stack or pass by testing it instead of the build under test.

  **It also fixed an accessibility bug it tripped over.** The combobox and currency fields pair a hidden input carrying the `name` with a visible control carrying the value, and `<Label htmlFor={name}>` pointed at that `name` — which is not an `id`, so those fields had no accessible label at all and `getByLabel()` could not see them. Adding `id` to the visible control was preferred over working around it with structural locators, so the spec now addresses those fields the way a screen reader does. `DatePicker` is knowingly left as it was: its trigger is a button, needing a different fix, and no test drives it. The dashboard's Net Worth figure gains a `data-testid` for a narrower reason — two links on that page point at `/dashboard/net-worth`, and nothing else distinguished the headline from the trend chart ([Issue #141](https://github.com/aellington89/finance-stack/issues/141), a v1.0.0 — Stabilization gate).

- **Coverage is now a gate rather than a report.** `app/vitest.config.ts` configured a v8 provider and no thresholds, so `npm run test:coverage` produced a number nobody was obliged to read — and CI never ran it at all, so a change that deleted a tested branch merged green. It now enforces a global floor of **85% statements / 75% branches / 83% functions / 86% lines**, plus per-area floors for `lib/**`, `scripts/**` and `components/**`, and `ci.yml` runs it on every PR. Each number is the measured baseline minus two points: enough to absorb ordinary jitter, not enough to absorb a regression. `thresholds.autoUpdate` is deliberately off — it rewrites the config from inside a CI run, and the resulting diff arrives with no author and no reason, which is the wrong shape for a gate whose whole value is being an explicit, reviewed number.

  **The thresholds are the visible half; the denominator is the half that took the work.** A threshold means nothing without a defensible answer to "percent of what", and the existing globs had an *accidental* one — three separate defects, each of which is easy to introduce again and none of which is visible in a passing run. First, `exclude: ["app/(app)/test-ui/**"]` **matched nothing**: parentheses are extglob alternation syntax, so the pattern only ever described a literal `app/app/test-ui/`, and the dev playground page was counted for as long as it existed. Second, `coverage.include` is applied with picomatch's `contains: true`, matching against any *substring* of the absolute path — which is why `app/**/*.ts` was silently admitting `scripts/`, `components/` and `next.config.ts`, and why **`*.ts` matches `*.tsx`** (`components/ui/card.ts` is a substring of `components/ui/card.tsx`). Third, and the consequence of the first two, `include` was governing two different filters at two different strictnesses: which *loaded* files get reported (loose, via `contains`) and which *untested* files get synthesised at 0% (strict, via tinyglobby). So `components/` contributed 9 of its 67 files — exactly those some unit test happened to import — while 58 stayed invisible, and adding the first test to any new directory would have moved the denominator underneath the threshold. The set is now an explicit allowlist of **51 files and 1518 statements**, and every exclusion carries its reason in the config.

  **What is excluded is a statement about the suite, not about the code.** Both vitest projects are `environment: node` and collect `*.test.ts` only, so nothing in the suite can mount a React tree — `**/*.tsx`, `hooks/**` and the Next.js `app/(app)/**` page tree are therefore out, because including files no test can execute makes the percentage a constant, and a constant cannot detect a regression. `auth.ts` is out for a sharper version of the same reason: `vitest-setup.ts` mocks `@/auth` wholesale for Issue [#120](https://github.com/aellington89/finance-stack/issues/120)'s session gate, so it can never report anything but 0% however well tested its dependents are. The five `scripts/` entrypoints are out because they are argv and stdout shells over sibling modules that stay in and sit near 100%. One cost was accepted rather than overlooked, and it is recorded in the config: five `tests/unit/components/` files exercise pure transforms that happen to be exported *from* `.tsx` components, so those transforms stop being counted — the tests still run and still gate behaviour. [#296](https://github.com/aellington89/finance-stack/issues/296) moves them into sibling `.ts` modules and adds a jsdom project, which is also what makes the `**/*.tsx` exclusion removable and what the issue's original "~70% for components" criterion actually required.

  **CI runs one test step where it ran two.** `Unit tests` and `Integration tests` are replaced by a single `Tests (with coverage)`, because a threshold checked against either half alone measures the wrong thing — `lib/queries` and `lib/actions` are ~840 of the 1518 statements and sit near 5% on a unit-only run — and keeping both plus a coverage pass would run the whole suite twice on every PR. The diagnostic value of the split survives: vitest prefixes every failure with its project name. Baseline at the time of writing, over the merged 743-test run: 87.5 / 77.3 / 85.4 / 88.1, with `lib/**` at 85.5% — comfortably past the ~80% the issue asked for. Branches is the weak metric across every scope and the one to watch ([Issue #142](https://github.com/aellington89/finance-stack/issues/142), a v1.0.0 — Stabilization gate).

### Changed

- **The image scan gate is green again: one OpenSSL advisory, `CVE-2026-14456`, turned all four images red at once.** It is the first finding to hit both base families simultaneously — `libcrypto3`/`libssl3` 3.5.7-r0 on `alpine 3.24.1` (`finance-app`, `finance-migrate`) and `libssl3t64`/`openssl`/`openssl-provider-legacy` 3.5.6-1~deb13u2 on `debian 13.6` (`finance-importer`, `finance-backup`) — so for once the single-file-for-four-scans simplification `.trivyignore` warns about costs nothing: every image genuinely reports it.

  **It is suppressed because the vulnerable code is unreachable here, not merely inconvenient.** The advisory is in the OpenSSL **QUIC server** path: an application that builds a Listener SSL object and accepts inbound connections with `SSL_accept()` will queue per-channel state for Initial packets with unknown connection IDs, without a bound, if it does not accept fast enough. Reaching it requires *being* a QUIC server. The four scanned images run `node server.js`, `migrate-and-seed.sh`, `python poll.py` and `pg_dump`/postgres — an HTTP/1.1 origin behind a reverse proxy, two psql clients and a file poller. None opens a QUIC listener, OpenSSL is reached for client-side and TCP TLS only, and Postgres has no QUIC support at all. The one component that could speak HTTP/3 is `caddy`, which is a stock `caddy:2.11.4-alpine` this repo neither builds nor scans, starts only under the `edge` profile, carries no `http3` directive in `caddy/`, and terminates TLS with Go's `crypto/tls` rather than OpenSSL.

  **The rebuild remedy was checked before reaching for a suppression, and the answer came out the opposite way from [#291](https://github.com/aellington89/finance-stack/issues/291).** There, the bases had not been rebuilt since the advisories landed, which is what justified the entry. Here all three *have* been rebuilt within days — `node:24-alpine` and `python:3.14-slim` on 2026-08-27, `postgres:18.6` on 2026-08-26 — and the CI run on 2026-08-29 pulled them fresh and still found the vulnerable versions. The fix exists in both distributions' package databases, which is what makes this a gating `fixed` finding rather than an unfixed one; it simply had not reached those rebuilds. So "wait and re-run" is not the fix, and every push since has effectively already tried it.

  **The expiry is deliberately short.** `exp:2026-10-06` rather than the `2026-11-17` every other entry in the file shares: those all clear on one Debian `util-linux` update, while this clears on an OpenSSL update already published in both distributions, which should arrive with the next base rebuild — weeks, not months. Surviving to October would itself be information, meaning two distributions' rebuilds have skipped a published fix twice, at which point the file's own standing advice to change the base image rather than extend a date starts to apply. Found while verifying [#141](https://github.com/aellington89/finance-stack/issues/141) in CI.

- **`.trivyignore` went backwards for the first time: eight of its fifteen entries were deleted because upstream had fixed them.** Nothing removes a suppression when the CVE stops being reported — `exp:` stops one *working*, it does not delete it — so an entry outlives its reason silently, and because one file backs all four scans it keeps silencing its CVE in every image, including ones that never reported it. That is the widening the file's header warns about, still costing something after the justification behind it is gone. `scripts/check-trivy-suppressions.sh`, which [#291](https://github.com/aellington89/finance-stack/issues/291) added for exactly this and which has never failed a build, named all eight on the CI run for this branch.

  **Two independent verdicts agreed, which is what made it safe to act on.** `node:24-alpine` shipped npm 11.19.0 with newer vendored dependencies — `tar` 7.5.16 → 7.5.19, `brace-expansion` 5.0.6 → 5.0.7, `undici` 6.26.0 → 6.27.0 — and Debian published the `util-linux` update. Read against those, every entry the reporter called dead names a fix version at or below what is now installed, and every entry it left alone names one above it. The whole `util-linux` batch went, taking the Debian-base section with it; four of the eight npm entries went; `tar` `CVE-2026-73566` survives because its fix is 7.5.21 and npm bundles 7.5.19. **A vendored bump clears some of a package's entries and leaves others**, which is the part worth remembering: three surviving comments had drifted a full release behind the image within weeks, still naming `tar 7.5.16` and `brace-expansion 5.0.6` as installed, and are corrected here. The verdict was taken from CI rather than a workstation, per the rule #291 wrote into the file after a local run deleted two live suppressions and CI went red on the next push ([Issue #303](https://github.com/aellington89/finance-stack/issues/303)).

That is the entire reason `deploy.sh` gates on a backup ([#228](https://github.com/aellington89/finance-stack/issues/228)) and the reason each release declares a `**Migration:**` marker ([#277](https://github.com/aellington89/finance-stack/issues/277)) — and until now it was folklore an operator would meet during a failed rollback rather than before one. The role to point it at is **`finance_bi`**, not the `finance_metabase` this issue was filed naming: that one was retired by [#250](https://github.com/aellington89/finance-stack/issues/250) after it turned out nothing had ever been pointed at it. Also here: `docs/roadmap.md` gains [#277](https://github.com/aellington89/finance-stack/issues/277), which was split out of this issue and then never registered, quietly violating the roadmap's own stated invariant that every milestone's issues are listed, and marks v0.3.0 released (it shipped 2026-08-15 and had never been ticked off); and the root `README.md` gains a short "Deploying to a server" section, since Getting Started is entirely checkout-based and nothing in it told a reader the bundle exists. Closes the [#223](https://github.com/aellington89/finance-stack/issues/223) epic ([Issue #229](https://github.com/aellington89/finance-stack/issues/229)).

  **And v1.0.0 stops being a vibe.** The roadmap called v0.4.0 "the 1.0 release candidate" while conditioning v1.0.0 on the phrase "stabilized in real use", which had no definition — so nothing distinguished *0.4.0 shipped* from *0.4.0 proved itself*, and the two could have been tagged on the same day. There is now a **v1.0.0 — Stabilization** milestone holding three gates: [#294](https://github.com/aellington89/finance-stack/issues/294), which requires the released bundle to have actually installed and upgraded on a real host, and [#141](https://github.com/aellington89/finance-stack/issues/141)/[#142](https://github.com/aellington89/finance-stack/issues/142), which move out of Phase 3 and stop being *recommended*. #294 exists because v0.4.0 is the first tag that publishes anything at all: at the moment it is cut, no image has reached GHCR and no bundle has been unpacked anywhere, so the "expose it safely" half of the 1.0 promise would otherwise rest on a deployment path that has never deployed. The security-epic condition the section used to name ([#100](https://github.com/aellington89/finance-stack/issues/100)) is closed and is retired from the text rather than left standing.
- **A deployment can now create its own first user**, which was the last thing a bundle install could not do for itself. There is no public registration, so the initial account comes from `npm run auth:create-user` — and neither published image could run it: the `finance-app` runner stage deletes npm, npx, yarn and corepack as attack surface ([#131](https://github.com/aellington89/finance-stack/issues/131)), while `finance-migrate` carried `npm`, `tsx`, `node_modules` and `app/scripts/` but **not** `app/lib/`, so that script's `@/lib/auth/roles`, `@/lib/db`, `@/drizzle/schema` and `@/lib/auth/password` imports resolved to nothing. A bundle install therefore came up **healthy and impossible to sign in to**, and the shipped workaround — run the CLI from a machine that *does* have a checkout, over an SSH tunnel to the host's loopback-bound Postgres — was precisely the checkout-with-Node that [#223](https://github.com/aellington89/finance-stack/issues/223) exists to remove. `finance-migrate` is the natural home and now carries `app/lib/`: it already has the script runner, already connects as the superuser, and already exists to do one-shot administrative work against the database, which is why it also hosts `verify-db-roles.sh`.

  **`app/tsconfig.json` is copied with it, and it is load-bearing rather than incidental.** `paths` is declared there, and it is the only reason the `@/…` specifiers resolve under `tsx` — which reads it through `get-tsconfig`, where `paths` without a `baseUrl` implies one of the tsconfig's own directory. Remove it as an unused config file and the `lib/` copy goes inert, with the failure appearing on a deployment host at first-user creation while every test in CI stays green. The copy is **whole rather than the three files the script actually reaches**, because `lib/` is ~350 KB against a `node_modules` already in that stage: a narrow copy buys nothing measurable and costs a tripwire that fires the first time anyone adds an import to one of those modules. `tsx` transpiles on demand, so files nothing loads are never resolved — `lib/db/audited.ts` sits beside `lib/db/index.ts`, imports `@/auth`, and is simply never reached. `dotenv` is now declared in `app/package.json` too: `create-user.ts` imports it and it resolved only as a hoisted transitive of `drizzle-kit`, which is a module-not-found on a deployment host waiting for a dependency bump to nest it.

  **The documented command carries no secret.** The `migrate` service gains a `DATABASE_URL` built from the `POSTGRES_USER` and `POSTGRES_PASSWORD` already in `.env`, in both compose files, so `docker compose run --rm --entrypoint npm migrate run auth:create-user -- <username>` is the whole invocation and the superuser password never reaches shell history or `ps` output. `migrate-and-seed.sh` is unaffected — it builds its own URL inline per `drizzle-kit` invocation. `deploy-smoke.yml` proves the guarantee in the only place it is provable, from the bundle alone with no checkout on the runner, and asserts the three properties that go with it: the account is created, re-running **upserts** to reset the password rather than adding a row, and the same command as `finance_app` is refused with `permission denied for table users` — which turns [#130](https://github.com/aellington89/finance-stack/issues/130)'s read-only grant on `users` into a tested property rather than a documented claim. Rejected: baking a script runner back into `finance-app`, which would undo #131's hardening for the sake of one administrative command, and a dedicated fifth image, which is a fifth build, a fifth Trivy scan and a fifth thing to publish to carry one command ([Issue #288](https://github.com/aellington89/finance-stack/issues/288), part of [#223](https://github.com/aellington89/finance-stack/issues/223)).
- **One command installs and upgrades a deployment, and it cannot skip its own backup.** `deploy/deploy.sh` ships in the bundle and replaces the remembered sequence the previous release documented: `./deploy.sh 0.4.1`, or no argument to converge on the `APP_VERSION` already in `.env`. It is idempotent — re-running it at the deployed version changes nothing — and **the ordering is the feature, not the command list**. The pull runs first, so a nonexistent or bad version fails before anything running is touched and before `.env` is written. The dump runs next and is a **gate**: `migrate` does not start until it lands, and a failed dump aborts the deploy with the old version still serving. That ordering is not a nicety, because `drizzle-kit` generates no down migrations — the moment a migration is applied, the only route back to the old schema is a dump that already existed. Two details in it are load-bearing and easy to get wrong: the dump runs with `--no-deps`, because `pg-backup` declares `depends_on: migrate: service_completed_successfully` and `docker compose run` honours it, so without the flag the command whose entire job is *dump before migrate runs* would start `migrate`; and it runs with `--entrypoint`, because that service's entrypoint is a `bash -c` sleep loop and a trailing `/scripts/backup.sh` would become the loop's `$0` rather than the program to run. An upgrade from a stopped stack is a supported path — the gate starts `postgres` on its own, at the old version, rather than declining to dump.

  **The health gate asserts one condition, not two in sequence.** `release.yml` polls `/api/health` until it returns 200 and then checks `build.version` once, which is correct on a fresh boot and wrong on an upgrade: the *old* container answers 200 with the *old* version while the new one is still starting, so a sequential check takes that first 200 and fails the version assertion immediately. The script polls until the response is 200 **and** reports the requested version, with only the 180-second timeout ending it. `curl -fsS` still exits non-zero on the 503 the route returns when the database is unreachable, so a degraded stack keeps the loop waiting rather than passing the gate. `jq` is used when it is installed and a text extraction when it is not, so the bundle's stated requirement is still Docker Engine and the Compose plugin.

  **On a failed gate it rolls back by itself** — prints the `migrate` and `finance-app` logs, re-pins the previous version, brings it up and re-polls — and then says the part that a rollback alone leaves untrue: **it restored the application, not the database.** Where the release carried a schema change, the old app may not run against the schema now on disk, so the script prints the pre-upgrade dump's path and the exact `restore.sh` invocation rather than implying the rollback was complete. The exit codes are a vocabulary meant to be branched on: `0` deployed, `1` aborted with nothing applied, `2` rolled back and healthy, `3` the rollback failed too. That last distinction is also why there is still deliberately no unattended upgrade timer — nothing automatic can decide whether a `breaking` release additionally needs its database restored.

  `.deployed-version` records what last *verified*, which is not what `.env` pins: a half-finished upgrade leaves `.env` at the new version and `.deployed-version` at the old one, and that difference is exactly the rollback target. `.env` is read, never sourced — it is the deployment's whole secret store and its values may contain `#`, spaces or shell metacharacters — and rewritten atomically with its mode preserved, since it is `600` on a deployment host. Superseded images are pruned on success **except the rollback target's**, so a rollback still works with the registry unreachable. `.github/workflows/deploy-smoke.yml` runs the whole thing — install, no-op re-run, a deliberately failing upgrade, automatic rollback — and asserts each guarantee; the "bad release" costs nothing to maintain, because `build.version` is inlined from `app/package.json` at image build time, so tagging the *same* image as `9.9.9` yields a container that starts, migrates and answers 200 while reporting the wrong version ([Issue #228](https://github.com/aellington89/finance-stack/issues/228), part of [#223](https://github.com/aellington89/finance-stack/issues/223)).
- Migration-reversibility marker: each release section in this file now carries a `**Migration:** none | backward-compatible | breaking` line declaring whether rolling back across it needs a dump restore. `drizzle-kit` generates no down migrations, so that question previously had no answer an operator could look up. The line is parsed into `ChangelogRelease.migration`, enforced by the changelog gate (missing on the release being tagged, or an unrecognized value anywhere, fails CI), shown as a badge on `/settings/about`, and carried into the published GitHub Release body. All eight prior releases were backfilled ([Issue #277](https://github.com/aellington89/finance-stack/issues/277)).
- `importer/Dockerfile` and `scripts/Dockerfile`: the importer and backup services now run from built images (`finance-importer`, `finance-backup`) rather than stock `python`/`postgres` images with the repo mounted over them. The importer bakes in `poll.py` and its pinned dependencies and runs as a non-root user, so it no longer runs `pip install` — and no longer needs internet access — on every restart. `finance-backup` is built `FROM` the same `postgres` tag the server runs, because `pg_dump` must be version-matched to it — bump the two together ([Issue #224](https://github.com/aellington89/finance-stack/issues/224), closing the Dockerfile half of [#132](https://github.com/aellington89/finance-stack/issues/132)).
- **A deployment bundle ships with every release**, so the unit of deployment is a small directory of configuration rather than a git checkout. `finance-stack-X.Y.Z.tar.gz` (plus a `.sha256`) is attached to each GitHub Release and unpacks to `/opt/finance-stack/`, carrying `compose.yml`, a `.env.example` with `APP_VERSION` already stamped to that release, a `finance-stack.service` systemd unit, the reverse-proxy config, a runbook, and the three bind-mount directories. A host needs Docker Engine and the Compose plugin; there is no source tree, no Node and no build toolchain, and nothing is compiled on the server — the images are the ones CI verified. `deploy/compose.yml` differs from the development `docker-compose.yml` in exactly two ways: every service this repo publishes is pinned to `${IMAGE_REGISTRY}/finance-<svc>:${APP_VERSION}` with no `build:` anywhere, so one tag moves the whole stack; and **`finance-app` binds `127.0.0.1:3001` rather than all interfaces**, extending the [#130](https://github.com/aellington89/finance-stack/issues/130) loopback pattern from Postgres and Metabase to the app tier, so a TLS-terminating proxy can be the only public listener. `docker compose up` from a checkout is unaffected and still builds from source. **Two compose files describing one stack will drift, so neither is left unguarded**: `release.yml` now runs its `/api/health` verification against `deploy/compose.yml` rather than the development one — the file that ships is the file that gets smoke-tested — with the images tagged under their final registry references *before* that boot, so they are verified under the names they publish under, and it additionally asserts that `finance-app` really is published on `127.0.0.1` and really is refused on the host's routable address. The complementary half is `scripts/check-deploy-parity.sh`, which runs on every pull request: it renders both files with `docker compose config`, asserts and then strips the three permitted differences, and fails on anything else — a resource limit, healthcheck, `depends_on` condition, environment entry or label changed in one file and not the other — as well as comparing the two `.env.example` variable sets, which may differ only by `APP_VERSION` and `IMAGE_REGISTRY`. One limitation shipped with this and did not survive the release: **creating the first user needed a checkout**, because the CLI requires the application source and Node and neither published image carried both. [#288](https://github.com/aellington89/finance-stack/issues/288) closed it by moving the CLI into `finance-migrate` — see the entry above ([Issue #227](https://github.com/aellington89/finance-stack/issues/227), part of [#223](https://github.com/aellington89/finance-stack/issues/223)).
- **A `vX.Y.Z` tag now publishes the four service images to the GitHub Container Registry**, so a server finally has an artifact to pull. `release.yml` already built `finance-app`, booted the whole stack and asserted `/api/health` reported the expected version and SHA — and then the runner was destroyed with the image on it. `finance-app`, `finance-migrate`, `finance-importer` and `finance-backup` are now pushed to `ghcr.io/aellington89/…` at both `:X.Y.Z` and the full 40-character commit SHA, which is the same value `/api/health` reports as `build.gitSha`, so a running container traces back to the health response that cleared it. **The ordering is the feature**: build → boot → verify → *then* push. The login and push steps carry no `if:` condition, so any earlier failure skips them — an image that fails its own smoke test never reaches the registry, and no GitHub Release is created for it either. The smoke test grew to cover what it now publishes: it previously asserted `finance-app`'s health alone, which would have published three images on the strength of a fourth image's health check, so `migrate` must now exit 0, `pg-backup` must reach `healthy` (which means a dump actually landed, proving `pg_dump` is version-matched to the server), and `importer` must still be running rather than restart-looping. Images are **`linux/amd64` only**, and deliberately so: verifying an image means *running* it, so an arm64 publish needs its own verified build rather than one more value in a `--platform` list. Each image also carries an `org.opencontainers.image.source` label, which is what links the GHCR package back to this repository. **First publish needs one manual step** — GHCR creates new packages private even from a public repo, so each of the four has its visibility set to Public once, after which pulls need no authentication ([Issue #226](https://github.com/aellington89/finance-stack/issues/226), part of [#223](https://github.com/aellington89/finance-stack/issues/223)).

None comes from code or a dependency this repo declares. **The first-choice remedy was checked rather than assumed**: `postgres:18.6` was last rebuilt 2026-08-15 and `python:3.14-slim` 2026-08-12, both before the advisories landed, so re-running the job could not have cleared it — which is what justified reaching for a suppression instead, and is now recorded in the entry rather than left as a claim. All four take the review date the entries they join already carry, because they clear as two upstream events that are each already represented on that date; giving them dates of their own would assert a distinction that does not exist ([Issue #291](https://github.com/aellington89/finance-stack/issues/291)).

  **The durable half is that nothing removed a suppression when the base was finally rebuilt.** The CVE simply stopped being reported and the line stayed in `.trivyignore`, inert but still silencing that ID across all four scans — including on images that never had the finding. `exp:` stops a suppression working; it does not delete it, and it fires months after the fact. `scripts/check-trivy-suppressions.sh` now runs at the end of the `image` job, re-reading the images with Trivy's `--show-suppressed` and emitting a warning annotation for every entry that no longer matches a finding anywhere. **It never fails the build** — a stale entry is not a vulnerability, and a gate that goes red for tidiness is a gate people stop reading. **And it comes with a caveat learned the hard way, which is now enforced in the script and the docs: only act on a verdict from CI.** Its first local run reported `setuptools 70.3.0` and `msgpack 1.1.2` as dead; both were deleted, and CI went red on the very next push because both are live. The check had faithfully reported the images *on the machine* — whose cached `python:3.14-slim` layer was three weeks older than the one CI pulls, and which therefore genuinely lacked packages CI's image has. (The corroborating `ls` was wrong too: they live under `pip/_vendor/`, not at the top level.) Both entries are back, the file holds fourteen, and the script now says so out loud when it is not running in CI — a locally built image is not the artifact the gate scans, and a stale base layer makes live suppressions look dead.

  **It is also built to fail safe, which matters more than it sounds.** Suppressed findings come back under `ExperimentalModifiedFindings` — experimental by name and liable to be renamed by a Trivy bump. The naive reading of a renamed field is "no entry matched anything", i.e. *every* suppression is stale, which is precisely the output that would get a dozen live suppressions deleted. Zero matches across all four images is therefore treated as "could not determine" and says so, never as a staleness verdict; the same applies to unparseable output, an unbuildable image, and `trivy` not being on `PATH` at all. Deliberately **not** done here: splitting `.trivyignore` per image, which its own header proposes once entries accumulate. The `util-linux` batch hits two images equally, so a per-image split would duplicate every shared-base finding — the pinned action accepts a comma-separated list of ignore files, so a split by *source* of finding is the better shape, and that is worth deciding on its own rather than under a red gate.

- Every service now runs this repo's code from an image instead of a bind mount, which is the prerequisite for deploying from a registry onto a host with no source tree ([Issue #224](https://github.com/aellington89/finance-stack/issues/224), part of [#223](https://github.com/aellington89/finance-stack/issues/223)). The `migrate` image bakes in `init-db/roles/`, `init-db/seeds/` and `scripts/verify-db-roles.sh`; `finance-backup` bakes in `backup.sh`, `restore.sh` and the balance-rebuild SQL used by `--profile init`. Everything lands at the path it was previously mounted at, so no script changed and every documented command — `docker compose exec pg-backup /scripts/restore.sh …`, `docker compose run --rm --entrypoint bash migrate /scripts/verify-db-roles.sh …` — still works verbatim. Only data stays mounted: `imports/`, `backups/` and `importer/parsers/`.
- **Editing `scripts/*.sh`, `init-db/roles|seeds/*.sql` or `importer/poll.py` now requires a rebuild** before it takes effect — previously the bind mounts made those edits live. `scripts/build.sh` builds all four images by default for this reason: a stale `finance-migrate` applies the seed and role SQL it was built with and reports success, which is a silent no-op rather than a failure. CI builds all four images on every PR, where it previously built only `finance-app` and so never compiled the `migrate` stage at all.
- The `changelog` additional build context is now named `repo`, and `CHANGELOG_CONTEXT` is now `REPO_CONTEXT` — it carries `init-db/` and `scripts/` as well as `CHANGELOG.md`.
- **Database creation moved out of the Postgres initdb hook and into the `migrate` job**, where every other piece of cluster setup already lives ([Issue #225](https://github.com/aellington89/finance-stack/issues/225), part of [#223](https://github.com/aellington89/finance-stack/issues/223)). `init-db/01-create-databases.sh` was mounted into `/docker-entrypoint-initdb.d/`, which Postgres runs **only on an empty data directory** — once, on first start, and never again. That is the identical trap [#130](https://github.com/aellington89/finance-stack/issues/130) moved the service roles out of for the same reason, and it was never specific to roles: a database added to that file would simply never appear on an existing volume, silently and with nothing to notice. It is now `init-db/roles/00-create-databases.sql`, applied as step 0 of `app/scripts/migrate-and-seed.sh` — which already runs idempotently on every `docker compose up`, already connects to `postgres` as superuser, and whose creation SQL was already `WHERE NOT EXISTS … \gexec`. **First install and upgrade become one code path**, and the `postgres` service loses its last bind mount, which is what lets #223 run a stock `postgres:18.6` on a host with no source tree. Three things fell out of the move. It is **SQL rather than shell** now, following `01-create-roles.sql`: the predecessor built its statements by expanding `${MB_DB_PASS}` into a heredoc, so a password containing a quote could break the statement or inject SQL, where `format(%I)`/`format(%L)` cannot — psql does not expand `:variables` inside dollar-quoted strings, hence `\gexec` rather than a `DO` block, the same constraint its two sibling files work around. **`MB_DB_PASS` now decides whether Metabase is provisioned at all** — empty skips the metadata role and database rather than creating a login role with a blank password, keeping "a cluster that never provisioned Metabase is a valid configuration" true rather than merely asserted; the existing `:?` guard still fires for the case it was written for, a metadata database that exists while `.env` has lost the credential. And **`FINANCE_APP_DB` finally works**: the old script hardcoded `Finances` while `migrate-and-seed.sh` honoured the variable, so setting it to anything else created one database and then tried to migrate a different, nonexistent one. One variable drives both now. The `postgres` healthcheck also moves from the unix socket to `pg_isready -h 127.0.0.1`, because during `initdb` the entrypoint runs a temporary server with `listen_addresses=''` — reachable on the socket but not on the network — so a socket check could report healthy and release `migrate` to fail on a refused connection, and since this change that first connection carries the entire first-install path. CI stands its cluster up with the real file instead of hand-written `CREATE DATABASE` psql, the same "one authority, exercised twice" it already applies to the roles files.
- **CI now Trivy-scans all four images, where it scanned only `finance-app`.** The other three were compiled but left unscanned on the grounds that their `postgres:18.6` and `python:3.14-slim` bases carry OS CVEs on an upstream fix cadence this repo does not control, and that blocking on those would buy a permanently red job rather than safety. Publishing them inverts that trade: an unscanned base is no longer one nobody depends on, it is one a deployment host pulls. The gate stays fixable-only (`ignore-unfixed`), and because those tags are rebuilt upstream, an OS-package finding on either usually clears on the next run with no change in this repo — which is now the first remediation step in CONTRIBUTING.md rather than a suppression. The four scan steps run independently of each other's result, so one red image shows the other three's findings in the same run instead of across four; they are gated on the build step succeeding, since scanning an image that was never built reports a missing image rather than a vulnerability. `.trivyignore` backs all four scans, so an entry silences its CVE in every image — a deliberate simplification recorded in its header, along with the `.trivy/<image>.trivyignore` split that replaces it if entries accumulate. Turning the gate on required seeding that file with ten findings, every one of them from a base image or bundled tooling rather than anything this repo declares: one `util-linux` CVE carried by both Debian bases, two packages the `python:3.14-slim` image bundles under pip, and seven in the dependencies `npm` vendors — which the `migrate` stage keeps deliberately, since it runs `npx drizzle-kit`, where the runner stage deletes npm for exactly this reason. Two prebuilt binaries are excluded at the scanner instead of by CVE: drizzle-kit's vendored `esbuild` and the postgres image's `gosu` are stripped Go binaries that nothing here compiles or rebuilds, so Trivy reports every Go stdlib advisory against them — 49 findings between the two — and suppressing those by id would mean a new entry each time the Go project publishes one, forever ([Issue #226](https://github.com/aellington89/finance-stack/issues/226)).

### Fixed

- **A fresh install produced no backup for its first 24 hours, and `pg-backup` sat `unhealthy` the whole time.** `pg-backup` waited on `postgres: service_healthy` alone, which stopped being sufficient the moment [#225](https://github.com/aellington89/finance-stack/issues/225) moved database creation into the `migrate` job. On an empty volume it started about five milliseconds after `migrate` and ran its first `backup.sh` roughly seven seconds before `Finances` and `metabase` existed, logged `database 'Finances' does not exist — skipping`, and then slept `BACKUP_INTERVAL_SECONDS` — a full day by default — before retrying. Its healthcheck passes only once a dump lands, so the container reported `unhealthy` for that whole window too. Nothing was wrong on an existing volume, where the databases are already there, which is why this survived #224 and #225 unnoticed: it is visible only on a first install. The fresh-install smoke test added in this release is what surfaced it. `pg-backup` now also waits on `migrate: service_completed_successfully` — the same gate `finance-app` and `importer` already use ([Issue #226](https://github.com/aellington89/finance-stack/issues/226)).

## [0.3.0] - 2026-08-15

**Migration:** backward-compatible

### Added

- **A role gate on the two lookup tables every KPI is computed from, and an admin screen to manage them.** `account_type_categories` and `transaction_types` define the balance-sheet groupings and the transaction classification the dashboard, accounting and work-expense views all report on, so a wrong edit there is not one bad row — it is every view at once. `users.role` had existed since [#120](https://github.com/aellington89/finance-stack/issues/120) with a default of `admin` and **nothing gated on it**; it is now a two-value vocabulary (`admin`, `user`) with a `CHECK` constraint, a new `requireAdminUser()` guard composing the existing session-and-rate-limit one, a new admin-only `/settings/admin` page carrying both tables, and a `--role admin|user` flag on `npm run auth:create-user`. All six mutators across the two tables sit behind the gate. `createTransactionType` — deleted outright by [#109](https://github.com/aellington89/finance-stack/issues/109) — is restored behind it, which is exactly where that issue said a legitimate insert belonged, taking the mutating-action count in [docs/input-validation.md](docs/input-validation.md) back from 17 to 18.

  **`/settings/categories` loses its Transaction Types card entirely**, which is what makes the first half of this issue true rather than nearly true. That card had no Add button after #109 and every one of the twelve rows the table ships is protected against rename and delete, so on a clean install it rendered twelve padlocks and offered no action at all. The only rows it could still act on were ones an install minted for itself past id 12 — and those were reachable by a **regular** user, because update and delete were gated on session alone. That was justified at the time on the grounds that protection already refused everything shipped; the reasoning had the sign backwards, since a self-minted reference row is precisely the user-owned data the KPI classification depends on. Protection and the role gate answer different questions — *does this row ship with the app* versus *is this table reference data* — and only the second one covers rows the constants cannot know about.

  **The role is read from the database on every guarded call, not from the session token**, and that is the part worth reading. Sessions here are 30-day JWTs with no server-side revocation, so a user demoted from `admin` would carry a cookie asserting `admin` until it expired — up to a month — which would make the whole gate a suggestion. One indexed lookup on a path taken only by lookup-table mutations buys an answer that is current in both directions: a promotion takes effect immediately too. An integration test signs in with a token claiming `admin` against a row that says `user` and asserts the refusal, so the lookup cannot later be optimised away without a failure. The token's `role` claim is still populated and still renders the sidebar's Admin link, where being a frame stale costs nothing. **The proxy is deliberately not a layer here**: it answers a denied request with a 302 to `/login`, which is the wrong answer for a signed-in non-admin — the same reasoning that kept `/api/health/seed-data` out of its matcher — so the page calls `notFound()` instead, and an admin route does not announce itself to someone who may not have one.

  **`/settings/categories` deliberately stays open to any signed-in user**, which resolves a standing contradiction between this issue and [#81](https://github.com/aellington89/finance-stack/issues/81). #81 proposed gating that whole page on `admin`; #87 requires the CRUD on `transaction_categories` and `account_types` to remain available to regular users, and [#111](https://github.com/aellington89/finance-stack/issues/111) sharpened the conflict by making that page where a category is tagged with a reporting role. #87 wins — naming your own categories is ordinary use, and the two dangerous tables moved out rather than the safe ones being locked down with them. #81's acceptance criteria are met in substance and it is superseded rather than outstanding; an integration test asserts a `role = 'user'` account can still create a category and an account type, so the decision cannot be quietly reversed. **Note for existing installs:** every existing account is already `admin` — that has always been the column default and nothing ever wrote another value — so nothing changes until you create a `user` with the new flag. Re-running `auth:create-user` without `--role` resets that account to `admin`, and the command now echoes the role it wrote ([Issue #87](https://github.com/aellington89/finance-stack/issues/87)).

- **Transaction categories carry a reporting role, so the Liabilities drilldown grows with your actual loan portfolio.** The Debt Service and Debt Waterfall aggregates identified debt activity by a hard-coded list of fifteen `transaction_category_id` values in `app/lib/queries/liability-categories.ts`. Those rows are **user data that ships nowhere**, which the seed-data taxonomy ([#178](https://github.com/aellington89/finance-stack/issues/178)) records as a defect rather than a category — the one cell where code hard-depends on a row the user may rename or delete. Two consequences, both real: a **fresh install reported zeros** across the whole tab, because it holds none of those ids; and a user who added `Personal Loan Principle` was **silently left out of the totals**, with no error and no way in short of a code change. `transaction_categories` now has a nullable `reporting_role` column (`debt_principle_paid`, `debt_interest_paid`, `debt_interest_accrued`, `debt_cash_paydown`), settable per category in `/settings/categories`, and the queries resolve membership against it at query time — so a category you add and tag is counted immediately. **The arithmetic is deliberately unchanged**: `payments` still sums the three paid legs and `principalPaid` is still `payments + interestAccrued`, so no number on the Liabilities tab moved. The four-way split makes the exact form (principal plus cash paydown, without relying on paid interest offsetting accrued interest over the period) a one-line change if it is ever wanted.

  **Generalised rather than liability-specific, on purpose.** The column is `reporting_role`, not `liability_role`, the keys are namespaced by domain, and the roles are declared as data in the new `app/lib/constants/reporting-roles.ts` that every consumer reads — queries, settings UI, CI gate and docs. A future `income_interest_earned` is a registry entry plus a CHECK widening, not a collision or a rename. Only the `debt` domain ships, because a permitted value no aggregate reads would mean nothing. The column is on `transaction_categories` alone: `transaction_types` and `account_type_categories` ship with the application, so naming a specific row of theirs by id is legitimate under the taxonomy, and a role column there would be one nothing reads.

  **The pinned lists are gone, and with them the protection rule that guarded them.** [#109](https://github.com/aellington89/finance-stack/issues/109) locked those fifteen rows against rename and delete — matched on id *and* name, so it was self-limiting on an install where those ids held unrelated rows — for the sole reason that the queries had no better handle on them. Renaming one now drops it out of nothing, so **those fifteen categories are fully editable and deletable again**. `lib/queries/protected-rows.ts` went too: it existed only to fetch a row's current name for that rule, so the guard is a pure predicate and three database round-trips leave the mutation path. **Note for existing installs:** migration `0005` backfills the roles onto exactly the categories the old lists named, matched on **id and name together**, so an install where id 7 is somebody's "Coffee" category is untouched. Anything the backfill did not match stays untagged and can be tagged in the UI. The backfill lives in the migration rather than in `shared-lookups.sql` because that file re-runs on every `docker compose up`, where an `IS NULL` guard would put a role back on a category you had deliberately cleared ([Issue #111](https://github.com/aellington89/finance-stack/issues/111)).

- **`npm run check:seed-references` gained two assertions, one of which closes a hole the other four were sitting on.** The **parser gate** is the important one: `parseSeedRows` reads `(<id>, '<name>')` tuples and nothing else, so giving one of the `transaction_categories` `INSERT` blocks a third column would not raise an error — every row in it would stop matching, the block would parse to zero rows, and the reference, shipped-set and fixture checks would all pass over an empty set **while reporting success**. That was not hypothetical: seeding `reporting_role` inline was the obvious way to write this change. It is now a CI failure naming the 2-tuple contract, and the roles are applied by separate `UPDATE` statements. The **reporting-role gate** proves the registry and the `CHECK` constraint in `drizzle/schema.ts` hold the same set in both directions — a role in the registry but not the constraint is a value the UI offers and the database rejects; one in the constraint but not the registry is a value the database accepts that no query reads. Generating one from the other would need `sql.raw`, banned repo-wide, so equality is proved rather than assumed — the same posture `SHIPPED_ROWS` has against the seed. The fixture-agreement half changes shape to match: instead of asserting every pinned id exists in `finances-test-mock-data.sql`, it asserts every reporting role is carried by at least one fixture category, which is the same guarantee — an aggregate reading a role no fixture row carries is one the integration suite cannot tell apart from zero ([Issue #111](https://github.com/aellington89/finance-stack/issues/111)).

- **Lookup rows the application owns can no longer be renamed or deleted.** `/settings/categories` handed the user every row in `transaction_categories`, `transaction_types` and `account_type_categories` with the same edit and delete buttons, drawing no distinction between a category they invented and one the app reads by id. Deleting a pinned liability category dropped a debt source out of the Liabilities drilldown with no error — just a smaller number — and renaming `transaction_categories` id 6 `Other` pinned `/api/health/seed-data` at 503 with no way back, since the seed is `ON CONFLICT DO NOTHING` and will not put a name back. Protected rows now render a lock with a tooltip explaining why, and the server actions refuse them so a crafted form submit gets no further. Two rules decide: everything `shared-lookups.sql` ships is locked **by id** (all 19 rows, whether or not any code names them — `transaction_types` id 3 `Refund` is nobody's constant, but it arrives identically on every install), and the ~15 liability categories the Debt Service and Debt Waterfall queries pin are locked **by id and name together**, so an install where id 7 is somebody's "Coffee" category locks nothing. The issue proposed a `protected` column; it ships instead as a predicate over the constants that already declare these rows, because a column is a second copy of a fact this repo already writes down — and the one time that duplication went ungated it survived four releases. `npm run check:seed-references` grew a fourth assertion proving the code-side list and the seed hold exactly the same rows, in both directions. **Note for existing installs:** the rule is "the name must equal the shipped name", not "this row is frozen" — so if you renamed id 6 before this landed, the UI still offers the rename that puts it back, and refuses every other one. ([Issue #109](https://github.com/aellington89/finance-stack/issues/109))

- **A seed-data taxonomy, and the gate that keeps it true.** Every lookup row now sits on two declared axes — does it *ship with the application*, and does *code depend on that specific row* — with the cross-product written down in [docs/database.md](docs/database.md). The cell that matters is the one holding rows the user owns that code nonetheless hard-depends on: that is recorded as a **defect, not a category**, resolvable only by shipping the row or by dropping the dependency. `transaction_categories` id 6 `"Other"` sat in it, which is why a brand-new empty `Finances` reported seed drift on a perfectly correct install — the row is written by `createAccount()` on every account opened with an initial balance, asserted by `SEED_REFERENCES`, and seeded nowhere. It now ships in `shared-lookups.sql`, and `transaction_categories` leaves the `TABLES_ALLOWED_ABSENT` escape hatch in `check-seed-references.ts`, which is now empty and meant to stay that way. **Note for existing installs:** the seed is `ON CONFLICT DO NOTHING`, so if you have renamed that category via `/settings/categories` your name is kept — and `/api/health/seed-data` will report drift on it where it previously said nothing. That is the honest signal, and locking the row against renames is Issue #87 ([Issue #178](https://github.com/aellington89/finance-stack/issues/178)).
- A third half to `npm run check:seed-references`, the **fixture agreement gate**. `transaction_categories` is defined in three places — `shared-lookups.sql`, `finances-test-mock-data.sql`, and the `beforeAll` upsert in `vitest-setup.ts` — and nothing held them together. The gate now asserts that every category ID pinned by `liability-categories.ts` exists in the `Finances_Test` seed under the expected name, and that the test hook is a *subset* of that seed rather than a second definition of it. Both checks reuse the existing `parseSeedRows` parser: the hook's SQL is a template literal but the same hand-authored `INSERT` shape, so it needs no special-casing. To give the gate names to check against, the two pinned ID lists in `liability-categories.ts` become `{ id, name }` tuples with the numeric exports derived from them, leaving every call site untouched ([Issue #178](https://github.com/aellington89/finance-stack/issues/178)).

### Removed

- **Transaction Types no longer accepts new rows from `/settings/categories`.** All 12 rows that table holds ship with the application, and a thirteenth was a row nothing in the codebase would ever recognise — no query filters on it, no importer parser maps to it, no `SEED_REFERENCES` entry names it — which is the same code-depends-on-a-row-the-user-owns defect the seed-data taxonomy calls out. The Add button is gone and `createTransactionType` was deleted rather than kept and made to always refuse, so the count in [docs/input-validation.md](docs/input-validation.md) drops from 18 mutating server actions to 17. Rows an install already created past id 12 are untouched and stay editable and deletable; a legitimate future insert belongs behind the admin screen in [Issue #87](https://github.com/aellington89/finance-stack/issues/87), with a role check of its own ([Issue #109](https://github.com/aellington89/finance-stack/issues/109)).

### Fixed

- **Four liability categories the Liabilities drilldown pins were missing from the `Finances_Test` seed**, so the debt-service and waterfall integration tests had been asserting totals computed over a short set since the drilldown shipped in v0.1.2. `finances-test-mock-data.sql` lacked ids 7 `HELOC Principle`, 8 `HELOC Interest`, 75 `Student Loan Principle` and 76 `Student Loan Interest` while claiming in a comment that "all of the relevant rows must be present here". The suite passed regardless, because `vitest-setup.ts` upserts a 24-row superset at startup and papered over the gap — which is precisely the failure mode the new fixture agreement gate exists to catch. The rows are added and the false comment corrected ([Issue #178](https://github.com/aellington89/finance-stack/issues/178)).

## [0.2.0] - 2026-08-09

**Migration:** backward-compatible

### Added

- Structured JSON logging and server-side error capture. Every record is a single line (`ts`, `level`, `msg`, plus `route` / `action` / `user_id` / `digest` where the call site knows them) emitted by the new `app/lib/log.ts`, so `docker compose logs finance-app | jq` works without a parser and pointing a log shipper at the stack later is a configuration change rather than a code change. Errors funnel through one choke point, `reportError()` in the new `app/lib/report.ts` — **the single place an error-tracking SDK gets wired**, which is why no SDK ships here: `@sentry/nextjs` would pull the OpenTelemetry package set into the blocking `npm audit --omit=dev` gate and the Trivy image scan, to ship pg error text off a stack the README says to keep on a trusted network. Three capture points, because one hook would miss most of what goes wrong: the new `app/instrumentation.ts` (`onRequestError`) catches unhandled server throws from page renders, route handlers and the proxy; the new `app/lib/actions/failure.ts` handles the eighteen server-action `catch` blocks, which never reach that hook because every action catches and returns an `ActionState` rather than throwing; and `app/(app)/error.tsx` plus a new `app/global-error.tsx` cover the client, the latter catching root-layout throws that the existing boundary sits below and so structurally cannot see. The client boundary is a correlation key, not a capture point — React redacts a Server Component error before it reaches the browser in production, leaving only a `digest`, which both records carry. **Redaction is the substantive part**: drizzle wraps every driver error in a `DrizzleQueryError` whose message is `Failed query: <sql>\nparams: <every bound value>`, so a naive `console.error(error)` on a failed insert logs the entire row — amounts, descriptions, account IDs — and repeats it in `err.stack`, which opens with `${name}: ${message}`. `serializeError()` cuts the message at the `params:` line and rewrites the stack header to match, keeping the parameterized SQL (placeholders, not values); driver fields are copied through an **allowlist** (`code`, `constraint`, `table`, `column`, `schema`) rather than a denylist, so pg's `detail` — which exists to echo the offending value back — and a future field cannot leak by default. `instrumentation.ts` logs `path` and `method` but never `request.headers`, which carry the session cookie. The residual is documented rather than papered over: `message` can still embed a value for some SQLSTATEs, so these logs warrant the same care as the database. `no-console` is now an ESLint error over `app/`, `lib/`, `components/` and `hooks/` (`scripts/` and `tests/` exempt — console output is a CLI's interface), making the third acceptance criterion a standing CI gate rather than a one-time assertion. `log.ts` and `report.ts` are deliberately isomorphic — no `@/auth`, no `next/*`, no database — because the client boundaries import them. New `LOG_LEVEL` env var (`debug`/`info`/`warn`/`error`, default and unrecognized-value fallback `info`). Documented in the new [docs/observability.md](docs/observability.md) ([Issue #129](https://github.com/aellington89/finance-stack/issues/129)).
- Audit logging for financial mutations: a new `audit_log` table recording actor, action, table, row key, and a full `jsonb` copy of the row before and after every insert, update and delete on `transactions`, `accounts` and the four lookup tables. It is written by a Postgres trigger (`audit_row_change()`, installed by the authored migration `0004_add_audit_log`), **not** by application code — which is what makes it cover the writers the app cannot see. The Python importer inserts into `transactions` directly as `finance_importer` and an operator can always reach `psql`; both are now recorded, attributed to their database role with `actor_source = 'database'`, with no change to `importer/poll.py`. Signed-in users are named because `auditedTransaction()` (new `app/lib/db/audited.ts`) sets two **transaction-local** GUCs the trigger reads; transaction-local is load-bearing, since `db` is a shared `pg.Pool` and a session-scoped setting would outlive the request on that connection and mis-attribute the next user's writes. That is also why the twelve bare `db.insert/update/delete` calls in `lib/actions/categories.ts` and the one in `updateAccount` are now wrapped — an implicit transaction has nowhere to put the actor. The trigger is `SECURITY DEFINER`, so `02-grants.sql` revokes INSERT/UPDATE/DELETE on `audit_log` from `finance_app` exactly as it already did for `users`: the app causes audit rows but can neither forge one nor delete one covering its tracks, and the grant gate now asserts both halves. `account_balance_history` is deliberately excluded — `rebuildAccountBalance()` rewrites an account's whole history on every write, so a trigger there would bury the signal under derived rows — as is `users`, which `finance_app` cannot write at all. Retention is indefinite with a documented manual prune rather than a scheduler; the log is readable through the new `v_audit_log` view, granted to `finance_metabase` alongside the other three. Documented in the new [docs/audit-log.md](docs/audit-log.md) ([Issue #180](https://github.com/aellington89/finance-stack/issues/180)).
- Two CI gates protecting the shared seed, both a consequence of it now being applied to the live database unconditionally (see Fixed, below). `npm run check:seed-references` gained a **seed contract** half asserting that every statement in `init-db/seeds/shared-lookups.sql` is additive and re-runnable — every `INSERT` carries `ON CONFLICT DO NOTHING`, every `UPDATE` carries a `WHERE`, and no `DELETE`/`TRUNCATE`/`DROP`/`ALTER` appears — so the properties the file used to merely claim in a comment now fail a PR instead of production. Comments and string literals are stripped before scanning, so prose naming the forbidden keywords (the file's own header lists them) and a seeded value legitimately named `'Delete'` do not trip it. Alongside it, a behavioural **reference backfill gate** in `ci.yml` builds a database in the exact state that caused #187 — user data present, one canonical row dropped — re-applies the real seed file, and asserts the row returns while account and transaction counts, and the liability liquidity classification, stay put ([Issue #187](https://github.com/aellington89/finance-stack/issues/187)).
- CI dependency and image gates: a blocking `npm audit --omit=dev --audit-level=high` on runtime dependencies (build-time dependencies are reported but non-blocking while the eslint 9 toolchain waits on `eslint-config-next` to support eslint 10), and a new parallel `image` job that builds the production image on **every PR** — previously it was only built on a `v*` tag, so a broken Dockerfile could reach `master` undetected — then scans it with Trivy, failing on fixable HIGH/CRITICAL findings. Documented exceptions go in the new `.trivyignore`, which requires a CVE, a rationale, and an expiry date per entry. CI's Postgres service image is pinned to `18.0` to match `docker-compose.yml` instead of floating on `18` ([Issue #131](https://github.com/aellington89/finance-stack/issues/131)).
- Dependabot (`.github/dependabot.yml`) watching five ecosystems weekly — npm (`app/`), pip (`importer/`), Docker (`app/Dockerfile`), Docker Compose (`docker-compose.yml`), and GitHub Actions — with npm updates grouped into dev and production sets so a routine week is two reviewable PRs rather than a dozen. Majors stay ungrouped. Auto-merge is deliberately not configured. To give the pip ecosystem a manifest to track, importer dependencies are now pinned in the new `importer/requirements.txt` and installed from it, replacing a Compose entrypoint that ran `pip install psycopg2-binary` unpinned on every container start ([Issue #131](https://github.com/aellington89/finance-stack/issues/131)).

- Scheduled database backups: a default-on `pg-backup` Compose service runs `pg_dump` (custom format) of the `Finances` and `metabase` databases into `./backups/` on an interval (default daily) with retention pruning, plus `scripts/backup.sh` / `scripts/restore.sh` (one-command restore into a clean DB, guarded against clobbering production DBs without `--force`) and a weekly `backup-smoke` CI workflow that seeds a known dataset, dumps it, restores it, and asserts a known row count to catch silent backup corruption. Documented in the new [docs/backups.md](docs/backups.md); tunable via `BACKUP_DBS` / `BACKUP_RETENTION_DAYS` / `BACKUP_INTERVAL_SECONDS` (see `.env.example`) ([Issue #122](https://github.com/aellington89/finance-stack/issues/122)).
- Session-based authentication (Auth.js/NextAuth v5, Credentials provider, JWT sessions): a sign-in page at `/login`, a sign-out control in the sidebar footer, a `users` table (authored migration `0003_add_users_table`) storing scrypt password hashes, and a first-user/password-reset CLI (`npm run auth:create-user -- <username>`). Requires a new `AUTH_SECRET` env var (see `.env.example` / `app/.env.local.example`) — documented in the new [docs/auth.md](docs/auth.md) ([Issue #120](https://github.com/aellington89/finance-stack/issues/120)).

### Changed

- **`/api/health` is now a liveness probe and nothing else; the seed-row drift check moved to a session-gated `/api/health/seed-data`.** The bundled endpoint from [#123](https://github.com/aellington89/finance-stack/issues/123) answered two unrelated questions in one request — *is the app alive* and *does the database still hold the reference rows the code depends on* — and the Compose healthcheck could not tell them apart. The consequence was that a **legitimate** state marked the container broken: a fresh `Finances` is seeded with only `account_type_categories` and `transaction_types`, while `transaction_categories` rows — including the `"Other"` row `OPENING_BALANCE_CATEGORY` asserts — are user-created, so a brand-new install returned 503 and Docker reported `finance-app` **unhealthy** while it was serving perfectly ([#178](https://github.com/aellington89/finance-stack/issues/178)). That is the wrong signal in the strong sense, not merely a noisy one: restart policy is driven by container health, and restarting cannot fix a missing row. The healthcheck therefore follows **liveness** deliberately — the URL it polls is unchanged, but what that URL now costs is one `SELECT 1` rather than that plus one indexed `SELECT … WHERE id IN (…)` per `SEED_REFERENCES` group, on a 10-second interval. `/api/health` keeps `build`, and no longer reports `seedData`.

  The new endpoint **requires a session and answers `401` without one**, which is the half of this that is a security change rather than a correctness one. The gate lives in the route handler rather than in `app/proxy.ts`'s matcher, for the reason `requireActionUser()` gates each action instead of trusting the proxy — and for one specific to this endpoint: the proxy answers a denied request with a 302 to `/login`, so a monitor following redirects would read a 200 HTML page as success. A 401 is the honest answer for a JSON route. Gating also keeps the `drift[]` payload's table names, ids and expected values off an unauthenticated response, and means an anonymous caller can no longer drive three indexed lookups per request against a route that was public precisely so it could be polled. The drift payload itself is preserved **verbatim**, so the response documented in [docs/database.md](docs/database.md) is still what you get — you now reach it signed in.

  The release smoke test changes shape as a result, and gains more than it loses. It had been pointing at `Finances_Test`, the fully-seeded fixture database, purely to dodge the fresh-install 503 — a workaround recorded in `.github/workflows/release.yml` since v0.1.4. With liveness no longer inspecting seed rows that dodge is unnecessary, so the job now boots a **brand-new, empty `Finances`** and additionally asserts that Docker itself reports the container `healthy`, which is the signal this change is about and the one polling the route directly cannot catch. What it gives up is the incidental proof that the fixture's reference rows were intact; that is covered on every push, and statically rather than at release time, by `npm run check:seed-references` ([#155](https://github.com/aellington89/finance-stack/issues/155)). Note this does **not** resolve #178 — a fresh `Finances` still reports drift on `transaction_categories` id 6 — it demotes it from a broken-looking install to a diagnostic you can read when you want it ([Issue #191](https://github.com/aellington89/finance-stack/issues/191)).

- **`@tanstack/react-table` moves to 9.0.0, and the one table in the tree is migrated to the feature-registration API.** v9 makes features opt-in rather than bundled, so the row-model helpers are no longer top-level exports: `getCoreRowModel` and `getSortedRowModel` do not exist on the package entry point at all, and the bump alone failed the build with six `Export ... doesn't exist in target module` errors from Turbopack. **The failure was only visible in the `image` job**, which is worth recording — `ci` runs lint and the test suites but never type-checks or builds the Next.js app, so a break of this shape is caught by the Docker build and nothing earlier. The migration is the real one rather than the `@tanstack/react-table/legacy` bridge, which ships `useReactTable` under the name `useLegacyTable` and is marked deprecated on arrival: `useReactTable` → `useTable`, with `tableFeatures({ rowSortingFeature, sortedRowModel: createSortedRowModel(), sortFns: … })` declared statically outside the component. The core row model is now automatic, so `getCoreRowModel` is simply dropped rather than relocated. Three consequences that are not obvious from the rename table: the `sortFns` registry has to name `alphanumeric` and `text` explicitly, because v9's auto sort-fn resolution looks those keys up by name and falls back with a dev-only `console.warn` when they are missing (the numeric `amount` column needs nothing, resolving to the built-in basic comparator); the column array needs `columnHelper.columns([...])` rather than a bare array literal, which is what preserves each column's `TValue` through inference and is otherwise a `TS2322` on the `columns` option; and `row.getVisibleCells()` belongs to `columnVisibilityFeature` in v9, so a table that registers only sorting has to call `row.getAllCells()` — an API missing because its feature was not registered, not because v9 removed it. The stale `react-hooks/incompatible-library` disable comment goes too: `useTable` no longer trips that rule, and ESLint reports the leftover directive as unused. Scope is one dev-only page, `app/(app)/test-ui/page.tsx`, which is `notFound()` outside development ([#257](https://github.com/aellington89/finance-stack/pull/257)).
- **ESLint 10 is ignored in `.github/dependabot.yml`, and the `^9` pin is now documented rather than incidental.** ESLint 10 removed the deprecated rule-context accessors — `context.getFilename()` and friends, superseded by `context.filename` back in 8.40 — and the plugins `eslint-config-next` vendors still call them, so 10.8.0 dies at rule-load time (`Error while loading rule 'react/display-name': contextOrFilename.getFilename is not a function`) before linting a single file. This is not one stale plugin: of the four that eslint-config-next 16.2.12 vendors, only `@next/eslint-plugin-next` accepts 10 — `eslint-plugin-react` caps its peer at `^9.7`, `eslint-plugin-import` and `eslint-plugin-jsx-a11y` at `^9`, `eslint-plugin-react-hooks` at `^9.0.0`. Nor is a config bump the way out: eslint-config-next 16.3.0 still depends on `eslint-plugin-react: ^7.37.0`, and 7.37.5 — still `latest` — is the only release satisfying it, so **no version of the Next lint config runs on ESLint 10 today**. Same reasoning as the TypeScript rule below: 10.8.1 is `latest` on npm, so without the ignore Dependabot re-raises the identical unmergeable PR every week ([#247](https://github.com/aellington89/finance-stack/pull/247) was the first, now closed). Staying on 9 is not drift — 9.39.5 carries npm's `maintenance` dist-tag — and the alternative, disabling the react, import and a11y rule sets, would trade real lint coverage for a dev-dependency bump. The declared range is deliberately *unchanged*: `^9` already means `>=9.0.0 <10.0.0`, which is exactly the ceiling wanted, so unlike the `~6.0` TypeScript pin there is nothing to tighten — what was missing was the `//eslint` note recording that the caret is load-bearing. Lifts once eslint-config-next ships plugins whose peers accept 10; `eslint-plugin-react` > 7.37.5 is the one to watch. 9.x minors and patches still arrive normally.

  The crash itself was already known — [#131](https://github.com/aellington89/finance-stack/issues/131) hit it when it first tried `eslint@10`, and [Issue #194](https://github.com/aellington89/finance-stack/issues/194) had been tracking it since as the thing keeping the build-time `npm audit` gate non-blocking. What was missing was the Dependabot rule, which is why #247 arrived to re-discover it; this change only stops the weekly re-proposal. **The link to the audit gate did not survive** — see the entry above under Security: that gate closed on eslint 9, so #194 is now about the gate alone and the eslint pin moved to its own tracker, [#263](https://github.com/aellington89/finance-stack/issues/263). The rule and its rationale are unchanged ([Issue #194](https://github.com/aellington89/finance-stack/issues/194)).

  Worth noting this one failed in `ci` rather than `image` — breaking the run of entries in this section that surfaced only in the production build — because linting is a thing `ci` actually does.

- **TypeScript moves to the 6.x line, and 7.x is pinned out.** The declared range goes `^5.6` → `~6.0` (resolving 6.0.3). The floor is unremarkable — every type package now declares `typeScriptVersion` 5.6, having converged there since [#215](https://github.com/aellington89/finance-stack/issues/215) derived it from `@types/node` alone. **The ceiling is the part worth reading.** `~6.0` rather than `^6.0` is deliberate: `typescript-eslint` 8.66.0 declares a peer of `>=4.8.4 <6.1.0`, so a caret would permit 6.1.x — a compiler the lint toolchain does not claim to support. Under `^5.6` that constraint was satisfied by accident, since the caret ceiling (`<6.0.0`) fell inside the peer range on its own; under a 6.x floor it no longer does, so the rule #215 established now has to be *stated* rather than inherited. A future 6.1 therefore needs its peer range checked rather than being waved through as a routine minor, which the `//typescript` note and `dependabot.yml` both record.

  **TypeScript 7 is ignored in `.github/dependabot.yml`, not merely un-adopted.** 7.x is the native port and does not expose the JS compiler API that `next build` drives for its type-check pass, so Next 16.2.12 refuses it outright (`TypeScript 7.0.2 does not provide the compiler API required by Next.js`); it is also outside typescript-eslint's peer range. Two independent blockers, neither resolvable here. Since 7.0.2 is `latest` on npm, leaving it un-ignored means Dependabot re-raises the identical unmergeable PR every week — [#246](https://github.com/aellington89/finance-stack/pull/246) was the first — and a permanently-red Dependabot PR is precisely how a genuine regression on some *other* bump gets waved through as "the usual red". The rule lifts when Next ships support and typescript-eslint widens; 6.x minors and patches still arrive normally.

  Once again the break surfaced only in the `image` job — the third entry in this section to end that way — and worse than its predecessors, since a compiler the framework cannot *host* reports as `failed to solve: … exit code: 1` at `Dockerfile:21` rather than as a type error ([Issue #195](https://github.com/aellington89/finance-stack/issues/195)).

- `app/components/ui/chart.tsx` now derives its tooltip and legend props from recharts' *default content* components (`DefaultTooltipContent` / `DefaultLegendContent`) rather than from the `Tooltip` / `Legend` wrappers. recharts 3 keeps `active` / `payload` / `label` in the chart's own store and injects them into whatever `content` renders, so it removed them from `TooltipProps` (they moved to a new `TooltipContentProps`) and likewise removed `payload` / `verticalAlign` from `LegendProps` — leaving `React.ComponentProps<typeof Tooltip>` no longer a description of what `ChartTooltipContent` actually receives. The default content components are what these two stand in for, so they are the honest source, and unlike `TooltipContentProps` they are exported by both 2.x and 3.x. Four call sites are widened to match: a shared readonly `TooltipDatePayload` for the nine per-grouping `labelFormatter`s in `accounting-chart.tsx` plus the one in `work-expenses-chart.tsx` (recharts 3 hands them a `ReadonlyArray`, which a mutable array parameter cannot accept), `interface TreemapNode` → `type TreemapNode` in both allocation charts (`Treemap.data` is now typed with a `[key: string]: unknown` index signature, and TypeScript gives object type aliases an implicit index signature but never gives one to an interface), and a `chartData` local in `net-worth-timeseries-chart.tsx` annotated as `Array<TimeSeriesPoint | PivotedRow>` (the data point type is inferred from the `data` prop, and an inline ternary pinned it to the first arm). Together these are the 18 errors across 8 files blocking [PR #205](https://github.com/aellington89/finance-stack/pull/205) — of which the image build reports only the first, since `next build` stops there. The change compiles clean under both 2.15.4 and 3.10.1, so it lands ahead of the bump and lets Dependabot rebase its own branch; under 2.15.4 it is behaviour-preserving, the sole non-type edit being a tooltip row `key` that falls back to the computed config key when `dataKey` is a function, which no chart here passes. As with the calendar fix below, the failure surfaced in `image` while `ci` passed — `ci` still does not run `tsc` ([Issue #195](https://github.com/aellington89/finance-stack/issues/195)) ([Issue #219](https://github.com/aellington89/finance-stack/issues/219)).

- Dropped the `table` key from the `classNames` object in `app/components/ui/calendar.tsx`. react-day-picker renders the month grid under the `month_grid` UI element; `table` was a v8-era name kept alive in v9 purely as a *typing* alias through the `DeprecatedUI` compatibility type, accepted by the compiler but never read at runtime — so `table: "w-full border-collapse"` had been dead code, applying neither class to the `<table>`. The calendar's layout comes from the flex rules on `weekdays` / `week` / `day`, which is why nothing ever looked wrong. react-day-picker 10 removes `DeprecatedUI`, turning the inert-but-accepted key into a hard type error that fails the production image build (`'table' does not exist in type 'Partial<ClassNames>'`) — the sole blocker on [PR #204](https://github.com/aellington89/finance-stack/pull/204). Because the key is already dead under 9.14.0 the removal is behaviour-preserving and lands ahead of the bump, letting Dependabot rebase its own branch rather than having it hand-edited. It is deliberately *not* remapped to `month_grid`: that would apply `w-full border-collapse` to the grid for the first time, a rendering change smuggled into a dependency upgrade. Worth noting the failure surfaced in the `image` job while `ci` passed — `ci` still does not run `tsc` ([Issue #195](https://github.com/aellington89/finance-stack/issues/195)) ([Issue #217](https://github.com/aellington89/finance-stack/issues/217)).

Copy the three keys in and run `docker compose up`; the roles and grants are applied to existing databases automatically. Metabase users must additionally re-point the Finances connection at `finance_metabase` once in the admin UI, since Metabase stores analytics connections in its own metadata database rather than in environment variables ([Issue #130](https://github.com/aellington89/finance-stack/issues/130)).

Moving the image and the test toolchain in one change is the point: Dependabot's `docker` ecosystem only reads Dockerfiles, so taking its PR alone would have left CI testing on 22 while the image shipped a different major ([Issue #210](https://github.com/aellington89/finance-stack/issues/210)).

Metabase supports LTS releases for 14 months and standard releases for roughly 2, so the newest tag is reliably the shorter-lived one: 0.58 is supported until 2027-02-17, while 0.63 goes EOL 2026-09-07 — six weeks after the PR was opened. Taking it would also have started a ~2-month upgrade cadence in which every hop runs a one-way schema migration against the `metabase` database, recoverable only by restoring that DB from `./backups`. ### Fixed

- **The two documentation indexes are now asserted against the `docs/` directory rather than remembered, and the drift they had accumulated is closed.** Every guide is listed twice — the `## Guides` list in `docs/README.md` and the `## Documentation` list in the root `README.md` — and both were behind. [#186](https://github.com/aellington89/finance-stack/issues/186) was filed against `docs/README.md`, which two guides had been added past; by the time it came up, [#182](https://github.com/aellington89/finance-stack/issues/182) had incidentally fixed that list and the root README was three behind instead (`secrets.md`, `audit-log.md`, `input-validation.md`). Fixing the list again would have bought until the next guide, so `npm run check:docs` now gates it in CI: every `docs/*.md` must be linked from both indexes, and every link in either index that points into `docs/` must resolve. The check reads the **list section**, not the file — the root README links `docs/secrets.md` from its Security prose while omitting it from the Documentation list, which is exactly how that one went unnoticed, and a whole-file search would have reported it as indexed. A renamed heading fails the gate rather than silently disabling it. The sweep the gate prompted also corrected four stale statements the release would otherwise have shipped: `CONTRIBUTING.md` still described the GitHub Release as published by hand (automated by [#175](https://github.com/aellington89/finance-stack/issues/175)), `docs/roadmap.md` still opened with "a personal-finance data store that today has no authentication" (shipped in [#120](https://github.com/aellington89/finance-stack/issues/120)) and was missing seven Phase 1 issues from its v0.2.0 list, and both `README.md` and `CONTRIBUTING.md` still asked for Node 22 (moved to 24 in [#210](https://github.com/aellington89/finance-stack/issues/210)).

- **The `finance-app` container healthcheck could never succeed, so the service reported `unhealthy` permanently regardless of what `/api/health` actually answered.** The probe fetched `http://localhost:3001/…`, and the container's `/etc/hosts` maps `localhost` to both `127.0.0.1` and `::1`; BusyBox `wget` tries the IPv6 address first, while the Next standalone server binds `HOSTNAME=0.0.0.0` — IPv4 only. Every check therefore died with `wget: can't connect to remote host: Connection refused` and the failing streak simply counted up (250 consecutive failures on the stack this was found on) while the route returned 200 to anyone asking from the host. The fix is to address `127.0.0.1` explicitly rather than to rely on name resolution picking the family the server happens to be listening on. This was found while verifying [#191](https://github.com/aellington89/finance-stack/issues/191), whose acceptance criteria are stated in terms of what the container healthcheck reports — they were not observable until the healthcheck could connect at all, and the container-health assertion #191 adds to the release smoke test would have failed on this. Worth noting what the bug concealed: `unhealthy` was the *correct* status for a different reason on installs affected by the seed-drift 503, so the two defects masked one another.

- The `migrate` service now applies `init-db/seeds/shared-lookups.sql` to `Finances` on **every** run instead of only when the database is empty. The old behaviour skipped the seed whenever `Finances` held any accounts or transactions — a row-count guard meant to protect real data — with the consequence that a populated database never received a reference row added to the seed after it was first created. Production had drifted exactly that way: it was missing `transaction_types` id 12 `"Opening Balance"`, which `/api/health` reports as `{"seedData":"drift","drift":[{"table":"transaction_types","id":12,"expected":"Opening Balance","actual":null}]}` with a 503, marking the `finance-app` container **unhealthy** — and, more than cosmetically, that row is the `NOT NULL` FK target `createAccount` writes for any account opened with a non-zero initial balance, so opening balances were failing against it. The guard was never what protected user data and its removal is not a relaxation: every statement in the file is additive (`INSERT … ON CONFLICT DO NOTHING`, `SELECT setval(…)`, and `UPDATE`s guarded by `WHERE liquidity_class IS NULL`), so applying it to a populated database is a no-op for everything the user owns. This is a structural fix rather than a one-row repair — the same silent drift would have followed every future addition to the seed. **No manual SQL is required:** the row is backfilled by the next `docker compose up`, and `docker compose run --rm migrate` is now the documented repair for any drifted lookup row ([Issue #187](https://github.com/aellington89/finance-stack/issues/187)).
- The `account_types.liquidity_class` defaults in `shared-lookups.sql` are now scoped to the four asset categories (`account_type_category_id IN (1,2,3,4)`) as well as to the known type names. Matching on name alone would have classified a liability that happens to share one — a user-created `Earmarked` filed under Current Liability, say — leaving the file's "Liabilities intentionally remain NULL" comment true only for as long as the naming convention held. Worth stating plainly, since these `UPDATE`s reach a populated `Finances` for the first time under the change above: `liquidity_class` does **not** decide asset vs. liability anywhere. That is `account_type_category_id` alone, and both queries that read the column (`getLiquidityBreakdown`, `getAssetTrendDecomposition`) already filter to the asset categories before consulting it, while no liability query reads it at all — so setting it cannot move an account between the two. The one visible effect on an existing install is the intended one: **asset** types that were never classified move out of the "unclassified" bucket in the Assets → liquidity breakdown into their proper bucket. Per-account overrides live in a different column and still win via `COALESCE(a.liquidity_class, at.liquidity_class)`, and `account_types.liquidity_class` is not settable from the UI at all, so there is no user intent to clobber ([Issue #187](https://github.com/aellington89/finance-stack/issues/187)).

### Security

- **The build-time `npm audit` gate now blocks, and it closed without the eslint 10 bump it was waiting on.** CI has run two dependency audits since [#131](https://github.com/aellington89/finance-stack/issues/131): a blocking one over runtime dependencies, and a second over the full tree carrying `continue-on-error: true`. The second was advisory-only because the eslint 9 dev tree held ~10 HIGH advisories whose only npm-offered fix was `eslint@10`, which `eslint-config-next` still cannot host — so [#194](https://github.com/aellington89/finance-stack/issues/194) parked the gate behind an upstream release nobody controls. **That precondition turned out to be an artefact of how `npm audit` reports fixes, not a real constraint.** npm names the fix it can reach by changing a *declared* dependency, which for a transitive four levels down is the nearest major it can bump — it does not say "this is already patched inside the range you resolved". All four of the HIGH advisories remaining today were: `brace-expansion` → 1.1.18 under `minimatch@3.1.5`'s `^1.1.7` and 5.0.9 under `minimatch@10.2.5`'s `^5.0.5` ([GHSA-rgw5-rvv9-x895](https://github.com/advisories/GHSA-rgw5-rvv9-x895)), `js-yaml` → 4.3.1 under `^4.1.0` ([GHSA-5p4m-2wfm-xmqj](https://github.com/advisories/GHSA-5p4m-2wfm-xmqj)), `picomatch` → 2.3.2 under `micromatch`'s `^2.3.1` ([GHSA-3v7f-55p6-f55p](https://github.com/advisories/GHSA-3v7f-55p6-f55p)), `fast-uri` → 3.1.5 under `ajv`'s `^3.0.1` ([GHSA-7p8r-x3mc-p8w7](https://github.com/advisories/GHSA-7p8r-x3mc-p8w7)). A targeted `npm update` of those four names cleared every one; `app/package.json` is untouched, no `overrides` entry was needed, and eslint stays on `^9`. Only `brace-expansion` is even in the eslint toolchain any more — the rest arrive through `shadcn`, the dev-only scaffolding CLI. **The two steps stay split even though the full-tree audit strictly subsumes the runtime one**, because which of them goes red is the diagnosis: runtime red means the advisory ships inside the image and usually needs an `overrides` entry, build-time red means a dev-tree bump. Merging them would cost a local re-run with `--omit=dev` to learn the same thing. What this does *not* buy is an escape hatch — `npm audit` has no per-advisory allowlist, so unlike [`.trivyignore`](.trivyignore) there is nowhere to record a HIGH with no available fix, and the gate would simply stay red; `esbuild` [GHSA-67mh-4wv8-2f99](https://github.com/advisories/GHSA-67mh-4wv8-2f99) is the live example, MODERATE today via `drizzle-kit` and "fixable" only by a breaking downgrade. That is left unbuilt deliberately rather than speculatively, and `CONTRIBUTING.md` now says so alongside the ordered fix procedure. The eslint pin outlives the gate that was entangled with it and moves to its own tracker, [#263](https://github.com/aellington89/finance-stack/issues/263) ([Issue #194](https://github.com/aellington89/finance-stack/issues/194)).
- **`.env` is now the single source of truth for four of the five database passwords, and the fifth says so out loud.** `POSTGRES_PASSWORD` and `MB_DB_PASS` both read like ordinary `.env` settings while neither took effect on an existing Postgres volume: the image consumes `POSTGRES_PASSWORD` only through `initdb --pwfile`, inside a branch the entrypoint skips once `$PGDATA/PG_VERSION` exists, and the same gate skips `/docker-entrypoint-initdb.d/`, so `init-db/01-create-databases.sh` — whose guarded `CREATE ROLE` had no matching `ALTER` anyway — never re-ran either. Editing either value left the stored password unchanged and desynchronized every service authenticating with the new one. **The inconsistency was the defect**, not the individual behaviours: the three service roles from [#130](https://github.com/aellington89/finance-stack/issues/130) rotate from `.env` alone because `01-create-roles.sql` re-issues an unconditional `ALTER ROLE … PASSWORD` on every `migrate` run, so two halves of one file behaved differently with nothing in it to signal which was which — and the trap was laid for exactly the operator hardening an existing stack. `MB_DB_PASS` now takes the same contract, folded into the `ALTER ROLE` that `03-metabase-role.sql` already issues rather than added beside it: one atomic statement, so that file's "a failure part-way leaves the role MORE privileged, never less" property survives, and the value is interpolated through `format(%L)` so a password containing a quote can neither break the statement nor inject SQL. It is required only when the metadata database exists, guarded inside that branch rather than globally, because a stack that never provisioned Metabase is a valid configuration and an empty value on one that did would quietly set a blank password. **`POSTGRES_PASSWORD` deliberately does not rotate, and the reason is worth stating because it is not fixable by adding another `ALTER`:** `migrate` authenticates *as* the superuser, so the moment `.env` and the stored password disagree it cannot connect — an `ALTER` it would have issued never runs, making re-assertion dead code on the one occasion it mattered. A two-value handshake (`POSTGRES_PASSWORD_OLD`) would genuinely rotate it, at the cost of a second secret in the file, a cleanup step to forget, and a fallback path where a wrong password silently succeeds via the old one — all to replace a two-command `\password` procedure on a single-operator stack. So the failure is made good instead: the new `app/scripts/preflight-superuser.sh` runs before anything else in the migrate job and turns a bare `password authentication failed` into the cause, the reason it cannot self-heal, and the exact procedure. It separates "wrong password" from "server not there" with `pg_isready`, which reports whether the server is accepting connections *without* authenticating and so answers that independently of locale — the message text is only a fallback, because a refused connection carries no SQLSTATE to key on, the same constraint `verify-db-roles.sh` works around with exit statuses. **Both halves are gated in CI**, following the shape of the #239 negative check: the rotation gate re-runs `03-metabase-role.sql` with a new password containing a quote and a backslash and asserts the **old** credential stops working — a gate checking only the new one would pass against a role whose password never changed — while the preflight gate drifts the CI cluster's superuser password out from under `.env` and asserts not just a non-zero exit but that the output still names `\password` and the docs anchor, since a message that degrades back to a raw psql error is the whole regression. `.env.example` now states which credentials rotate in place, and `docs/database.md` tells one rotation story covering all five instead of a caveat listing exceptions ([Issue #189](https://github.com/aellington89/finance-stack/issues/189)).
- **`nanoid` reached the runtime tree at 3.3.16, which carries [GHSA-2v37-7h3g-55p8](https://github.com/advisories/GHSA-2v37-7h3g-55p8) (HIGH)** — custom generators can loop indefinitely when `size` is zero. It arrives through `next` → `postcss`, which is already overridden here, so the fix is a floor move rather than a new entry: the `^8.5.23` pin that first cleared postcss's own advisory in [#131](https://github.com/aellington89/finance-stack/issues/131) ranges on `nanoid ^3.3.16`, and 8.5.26 is the first postcss release to require `^3.3.17`. The override is now `^8.5.26` so a fresh resolve cannot land back on a vulnerable nanoid, and the lockfile moves postcss 8.5.23 → 8.5.26 and nanoid 3.3.16 → 3.3.18. Worth recording that this was **failing the `npm audit --omit=dev --audit-level=high` gate on master itself**, not on one branch — every open Dependabot PR inherited the red `ci` job from the base, which is exactly the state in which a real regression on one of those PRs would have gone unnoticed.
- **`finance_metabase` is retired**, leaving one role for one job. Adding `finance_bi` below left the stack with two credentials that both read as "Metabase's connection to Finances, entered by hand in the admin UI", both required to be non-empty for `migrate` to run, and exactly one of them ever wired to anything — `finance_metabase` was created in [#130](https://github.com/aellington89/finance-stack/issues/130) and never pointed at in the entire time it existed. That is not a choice, it is a footgun: it is how an operator wires up the wrong one, and it produced a "what is the difference between these two?" question within minutes of `finance_bi` landing. Retiring it is a real step away from the stricter posture and is recorded as such — views-only means Metabase cannot see a base table *at all*, which `finance_bi` does not give you — but that posture was never actually in force here, and the route back is the [#249](https://github.com/aellington89/finance-stack/issues/249) follow-up: write views covering `account_balance_history`, rebuild the questions on them, then re-introduce a views-only role. **Removing it from the SQL was not sufficient on its own**, which is the part worth knowing: the role would linger on any existing volume, and the #239 attribute sweep would then correctly fail it as an undeclared login role holding `CONNECT` — a fix that breaks the gate it was merged beside. So the retirement is active. `02-grants.sql` issues a guarded `DROP OWNED BY` per database to strip its privileges, and `migrate-and-seed.sh` then issues the cluster-global `DROP ROLE`, which can only succeed once every database has been cleaned. That `DROP ROLE` is deliberately **non-fatal**: `migrate` gates `finance-app` startup through `service_completed_successfully`, so aborting the whole stack over a legacy role that nothing uses would be a far worse outcome than leaving it in place — and a role that survives is not silently tolerated either, since it has no privileges left and the #239 sweep fails it the next time the gate runs. Loud, but not destructive ([Issue #250](https://github.com/aellington89/finance-stack/issues/250)).
- **Metabase's connection to `Finances` was the `postgres` superuser**, while the README and `docs/database.md` both said it "sees the three views and no base tables". The `finance_metabase` role from [#130](https://github.com/aellington89/finance-stack/issues/130) was created, granted and gated correctly — and then never pointed at, because doing so is a manual step in the Metabase admin UI that no `docker compose up` can apply and no gate can see. The least-privilege work landed in the repository and never landed on the cluster, which is the same shape as the `metabase_user` finding below. It surfaced as a broken symptom rather than a review: `POSTGRES_PASSWORD` was rotated during [#181](https://github.com/aellington89/finance-stack/issues/181) — correctly, following this project's own guidance — while Metabase's stored connection kept the old literal from `2208ce6`, so every chart began failing with `FATAL: password authentication failed for user "postgres"`. Metabase had been down since the rotation, so nothing surfaced it until the stack was next started. **`finance_metabase` could not simply be adopted**, which is why this is a new role rather than a config change: all 43 questions are built on base tables (21 on `transactions`, 22 on `account_balance_history`), that role holds `SELECT` on the four views and explicitly nothing on any base table, and 22 of those questions have no view to migrate to at all — `v_account_balances_current` is current balances per account, not the history series. So the new **`finance_bi`**: `SELECT` on the seven core base tables *and* the four views, no write anywhere, and **nothing on `users` or `audit_log`**. That exclusion is the entire reason it exists rather than reusing `finance_app`, which already holds `SELECT` on everything and would have served the same questions unchanged — it can also read `users.password_hash`, and Metabase permits native SQL, so marking the table hidden in its admin UI is a display setting rather than a privilege boundary. The grants are **enumerated** rather than `GRANT … ON ALL TABLES` followed by a `REVOKE`, for the reason `finance_importer` and `finance_metabase` are: when the exclusions are the point, a broad grant plus a revoke re-exposes `users` the first time someone re-runs it with the revoke dropped. `finance_metabase` is unchanged and stays the stricter, preferred option for any deployment whose questions all sit on views. The exclusions are asserted by name in `assert-grants.sql` and proved behaviourally in `verify-db-roles.sh` by connecting as the role, so neither can quietly stop being true. `docs/database.md` now tells you to **check what the connection is actually set to** rather than assuming, with the query to do it ([Issue #249](https://github.com/aellington89/finance-stack/issues/249)).
- **`metabase_user` was a superuser**, and the role-attribute gate had never had an opinion about it. `init-db/01-create-databases.sh` creates Metabase's metadata-DB role as `CREATE ROLE … WITH LOGIN PASSWORD` and nothing else, so every reading of this repository said "scoped login"; the live cluster's role carried `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `REPLICATION` **and** `BYPASSRLS`, widened out-of-band at some point with nothing committed to record it. Two consequences, and they compound: `MB_DB_PASS` was a superuser credential rather than the narrowest of the four database passwords — and one of the two that [#189](https://github.com/aellington89/finance-stack/issues/189) says cannot be rotated from `.env` at all — and a second superuser login sitting beside the least-privilege roles undoes in practice what [#130](https://github.com/aellington89/finance-stack/issues/130) established, since "none of them is a superuser" described those three roles and not the cluster. **The machinery to catch this already existed and was pointed at the wrong set:** `assert-grants.sql` checks exactly these five attributes, but iterated `ARRAY['finance_app','finance_importer','finance_metabase']`, so the drift was not missed so much as never looked at. It now sweeps every login role in `pg_roles`, exempting only `current_user` — the identity running the gate, which is deliberately the maintenance superuser. `current_user` rather than a hardcoded `'postgres'` keeps `POSTGRES_USER` configurable, and rather than a psql `:variable` because a `DO` block cannot read one: the same constraint `01-create-roles.sql` works around with `\gexec`. The cost of that choice is that the file now only asserts what it appears to when run as the maintenance superuser, which is stated in its header and in the docs; every existing caller already satisfies it. A role the stack does **not** declare must additionally hold no `CONNECT` on the database under test, which is what contains the metadata role out of `Finances` rather than merely making it non-superuser. **On out-of-band changes the stack now tells one story:** it silently converges what it declares — matching how `02-grants.sql` has always revoked before granting — and refuses to be silent about anything else, so a login role added deliberately by an operator fails the gate rather than being quietly overruled on the next `up`. The convergence itself is the new `init-db/roles/03-metabase-role.sql`, applied by the `migrate` service and therefore reaching existing volumes, which is the whole reason it cannot live in `init-db/` (that script runs once, on an empty `PGDATA`, which is exactly how the drift became uncorrectable). **Its statement order is load-bearing and not incidental:** Metabase runs its own Liquibase migrations against its metadata database at startup, so ownership and `USAGE`+`CREATE` on that database's `public` schema are established *first* and the attributes stripped *last* — the reverse order can leave Metabase unable to migrate itself, and nothing is wrapped in a transaction precisely so that a failure part-way leaves the role more privileged than intended rather than less. It does not touch `PASSWORD`: half-solving #189 in the one place someone would later assume was authoritative is worse than not solving it. The audit also turned up that `PUBLIC` still held the default `CONNECT`/`TEMPORARY` on the metadata database — every role in the cluster could open a session on the database holding Metabase's own user table — so that is revoked too, mirroring what `02-grants.sql` has always done on the `Finances` side. **Verified against a running Metabase, not just the catalog**, because the failure mode is at startup migration and no catalog assertion would see it: under `--profile bi`, Metabase v0.58.21 came up healthy on the de-privileged role with zero permission errors in its log, Liquibase acquired its migration lock and reported "Database Migrations Current", and its Quartz scheduler was still writing check-ins to the metadata DB seconds later — with all 3 dashboards, 84 questions and 3 connections intact. `scripts/verify-db-roles.sh` encodes the cheap version of that as four new cases (create+drop a table in the metadata DB; `CREATE ROLE` and `CREATE DATABASE` refused; no connection to `Finances`), which needed a second helper: a refused *connection* is reported by libpq before psql has a session, so `VERBOSITY` never applies and the message carries no SQLSTATE for the existing `42501` test to match. Keying the new helper on psql's exit status instead surfaced a latent hole in the old one — an `allow` case asserts the *absence* of a `42501`, which a connection that never opened also satisfies, so a wholly wrong password had been able to sail through every allow case in the file. Exit status 2 now fails a case in either mode. Finally, CI grows a **negative check**: it widens `metabase_user` to superuser, adds an undeclared superuser login, and adds an attribute-free role holding `CONNECT`, asserting the gate rejects each and reverting all three — a gate that cannot fail proves nothing, and this one reported OK for months while a superuser sat beside the roles it was checking ([Issue #239](https://github.com/aellington89/finance-stack/issues/239)).
- Secret-management audit and a documented production secret-sourcing model, closing the last un-broken-out slice of the security epic ([#100](https://github.com/aellington89/finance-stack/issues/100), which closes with this release). The audit itself came back clean on the thing it most needed to: across the working tree and all 134 non-merge commits, `.env` and `app/.env.local` have **never** been tracked, `docker-compose.yml` interpolates every credential as `${VAR}` with no `:-default` fallback, both `.env*.example` templates carry only `changeme` placeholders, and a full-history gitleaks scan under the default ruleset reports nothing. What it did find was that **the ignore rules were narrower than they read**: the root `.gitignore` listed `.env` and `app/.env.local` *literally*, so `.env.production`, `.env.local`, `.env.bak` and friends at the repo root were all stageable by a plain `git add .`, and `app/.dockerignore` — which is the one that governs the shipped image, since Compose sets the `finance-app` build context to `./app` — excluded `.env.local` and `.env*.local` but not a bare `.env` or `.env.production`. That second gap is the sharper one, and worse than it reads: the runner stage looks safe because it copies `.next/standalone` rather than the source tree, but **`next build` copies every `.env*` file it finds into `.next/standalone`**, so the file ships inside the finished image *verbatim*. That was measured rather than reasoned about — planting an `app/.env.production` and building under the old rules puts `/app/.env.production` in the image with its contents intact, and the same tree under `.env*` leaves no `.env` file anywhere under `/app`. Both are now globs (`.env*`, with `!.env.example` as the single exception at the root and **no** exception under `app/`). The new `tests/unit/ignore-coverage.test.ts` is what stops them narrowing again, asserting through `git check-ignore` that twelve `.env` variants are ignored and that the two committed templates are not — `--no-index` is load-bearing there, because ignore rules do not apply to tracked paths and without it the template assertions could never fail. Secret scanning lands as its own workflow rather than a job in `ci.yml`, because gitleaks' scan scope follows the event: `push` and `pull_request` scan only that commit range, while `schedule` and `workflow_dispatch` scan the full history, and folding it into `ci.yml` would have meant either dropping the weekly sweep or running the whole postgres-plus-image-plus-Trivy suite on a cron to get it. There is deliberately **no `.gitleaks.toml`** — the default ruleset scans this history clean, so a config today would hold nothing but speculative allowlists, and a broad allowlist added "just in case" is exactly how a real secret gets waved through later. On sourcing, the answer is **environment variables from one `chmod 600` `.env` on the deployment host, never in an image**, and Docker secrets are recorded as considered-and-rejected rather than left silent, since [#189](https://github.com/aellington89/finance-stack/issues/189) defers the question here: `postgres` and `metabase` support `*_FILE`, but `finance-app` and `importer` consume a *composed* `DATABASE_URL` with no `_FILE` equivalent, so adoption means an entrypoint shim on the startup path of every service — to keep credentials out of `docker inspect`, which is only reachable by an attacker who already has root-equivalent Docker socket access and can read the file anyway. The audit's one live finding is recorded in the new [docs/secrets.md](docs/secrets.md) along with its resolution: the initial commit `2208ce6` hard-coded `POSTGRES_PASSWORD: password` and `MB_DB_PASS: password` before `2d42bd2` replaced them with `${VAR}` references, and those literals are still readable in this public repository's history. The history was **not** rewritten — the exposed value is a dictionary word, and invalidating every clone and every commit reference in the changelog and issues buys no reduction in risk. Rotation is what closes an exposure like that, and since neither of those two variables rotates from `.env` (the trap #189 exists to fix), the guide documents the `\password` route and states plainly that any deployment whose `.env` still holds a value appearing in this repository's history is holding a public credential ([Issue #181](https://github.com/aellington89/finance-stack/issues/181)).
- Edge hardening: security headers, sign-in and mutation rate limiting, and a documented exposure posture with TLS termination available as an opt-in Compose profile. **Security headers** are declared in `app/next.config.ts` rather than in `app/proxy.ts` or the proxy container, because the proxy's matcher covers four page trees and would have missed `/`, `/login`, `/api/*` and `/_next/*` — most of what an unauthenticated caller can reach — whereas `headers()` compiles into the routes-manifest and applies to everything the server emits, including static assets, in every posture and independent of any proxy being configured correctly. The set is a CSP plus HSTS, `X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy` and `Cross-Origin-Opener-Policy`; `poweredByHeader` is now `false`, since `X-Powered-By: Next.js` had been naming the framework on every response. The CSP **keeps `'unsafe-inline'` on `script-src` and `style-src`**, which is stated rather than glossed: `next-themes` injects an inline script to set the theme before first paint, and `components/ui/chart.tsx` injects a `<style>` element carrying each chart's colour variables, so removing it needs a per-request nonce threaded through both — a tracked follow-up. What the rest of the policy still buys is real, because the app loads no third-party script at all: `default-src`/`connect-src 'self'` leave injected script nowhere to send data, `form-action 'self'` stops the sign-in form being retargeted, `base-uri 'self'` stops `<base>` rewriting every relative URL, and `object-src 'none'` removes the plugin surface. HSTS is sent unconditionally — browsers ignore it over plaintext by specification — without `preload`, whose submission is effectively irreversible for a hostname the project does not own. **Rate limiting** is a zero-dependency in-memory fixed-window counter (`app/lib/security/rate-limit.ts`), following the reasoning already recorded in `lib/report.ts` for shipping no error-tracking SDK: there is no Redis in the stack, a Postgres write per login attempt would make the limiter its own amplification vector, and a new runtime dependency lands in the blocking `npm audit --omit=dev` gate and the Trivy scan. The sign-in budget (five failures per username per 15 minutes, cleared by a success) is enforced in the new `app/lib/auth/authorize-credentials.ts`, which is the **one path every credential attempt reaches** — the login form posts to `/login` as a *server action*, not to `/api/auth/*`, while `/api/auth/callback/credentials` is directly POST-able, so limiting either route alone would have left the other open. It is checked before the password is verified, so a blocked attempt costs no `scrypt` comparison, making it a denial-of-service control as much as a brute-force one; that module exists separately from `auth.ts` for the same reason `verifyCredentials` does, since `next-auth` reaches for the `next/server` runtime Vitest cannot provide and the enforcement path would otherwise be untestable. The mutation budget (120 per signed-in user per minute) rides inside `requireActionUser()`, so all 18 guarded actions and every future one are covered by construction rather than by remembering a second line per action. Two limitations are documented rather than papered over: counters live in process memory, so they reset on container restart and do not span replicas, and the sign-in limit is keyed on **username, not IP** — the app cannot see a trustworthy client address in the default posture, and the consequence is that someone who knows the username can hold the real user out for up to 15 minutes. Rejections log a `warn` record carrying `scope` and `entry_point` and deliberately **no username**, since the username field is exactly where a mistyped password lands. `/api/health` is not limited, as the Docker healthcheck polls it every 10 seconds. **TLS** ships as a `caddy` service under `--profile edge` with automatic certificate issuance, switched off and changing nothing about how the app is reached today — `finance-app` keeps its `3001` binding. The new [docs/deployment.md](docs/deployment.md) states the trusted-network vs public-internet postures as a checklist rather than a warning, and the README's "keep it on a trusted network until those land" paragraph now describes a gated stance instead of an open gap. The header set is asserted in CI by a unit test over the config and again against a running container by the release smoke test ([Issue #182](https://github.com/aellington89/finance-stack/issues/182)).
- Input-validation and error-message audit across the whole mutation surface, closing the last un-broken-out slice of the security epic. The headline defect was **ID parsing**: sixteen of the eighteen server actions narrowed their ID with `Number(formData.get(…))` behind a `!id || id <= 0` guard, which rejects `NaN`, `""` and `0` but passes `1.5`, `Infinity`, and anything past the `int4` ceiling — all of which are fine JavaScript numbers that bind straight onto an `integer` column and raise `22P02` / `22003` **in the driver**. In the five `delete*` actions the "is it still in use?" pre-check ran *outside* the `try`, so that error escaped the action entirely: `?accountId=1.5` was an unhandled throw and a 500, not a validation error. Every ID now goes through one schema, `parseEntityId()` in the new `app/lib/validations/id.ts`, and every read that touches the database has moved inside the `try` so that the only way out of a server action is an `ActionState`. The same ceiling was missing from the foreign-key fields *inside* the form schemas, whose `Number.isInteger(Number(val)) && Number(val) > 0` refinements are right about `1.5` but have no upper bound — they now share the schema via `isEntityId()`, so the two checks cannot drift apart again. The read path had the identical hole: `/accounts/1.5/edit` and `?accountIds=1.5` threw during render, and `?amount=abc` reached a `numeric` comparison; the new `app/lib/validations/search-params.ts` owns those params (and absorbs the `get`/`getNumberArray`/`getStringArray` helpers that were duplicated verbatim in the Transactions and Accounting pages), pairing with the existing `validateDateRange()` from [Issue #150](https://github.com/aellington89/finance-stack/issues/150). **One behaviour change worth stating:** a filter list containing an invalid entry is now rejected whole rather than filtered down to its valid entries — silently querying the remainder answers a question the user did not ask, and that filtering (`.filter((n) => !isNaN(n))`) is precisely what let `1.5` through, since `Number("1.5")` is not `NaN`. Separately, every `z.string()` in `lib/validations/` gained an authored message: a field the client omits arrives as `null` and a bare `z.string()` renders that as `Invalid input: expected string, received null`, which `buildFieldErrors()` put straight on the form ([Issue #179](https://github.com/aellington89/finance-stack/issues/179)).
- `sql.raw()` is **eliminated from the application and banned by ESLint**, over the same four directories as the `no-console` rule from [Issue #129](https://github.com/aellington89/finance-stack/issues/129). It splices its argument into the SQL text unescaped, and the audit found a URL search param reaching it: `lib/queries/accounting.ts` built its `generate_series` window as ``sql.raw(`date_trunc('${truncUnit}', '${dateFrom}'::date)`)``, with `dateFrom` held back from the query text by nothing but the `^\d{4}-\d{2}-\d{2}$` regex in `safeDate()`. Not exploitable as it stood — which is why this is a hardening entry and not a patched vulnerability — but a regex is the wrong last line of defence, and the surrounding raw-interpolation habit is what put it there. All 29 call sites had a bound equivalent: `date_trunc`, `to_char` and `generate_series` take their unit, format and step as ordinary parameters, so the fixed expression maps became `Record<K, SQL>` fragments instead of strings, the constant type-ID lists became a new `valueList()` helper, the column aliases became `sql.identifier()` (escaping that is only safe on the pinned `drizzle-orm ^0.45.2` — the release that fixed identifier-escaping injection, see the [#131](https://github.com/aellington89/finance-stack/issues/131) entry below), and the `tableAlias` parameter no caller ever passed was deleted. With zero legitimate uses left the rule is absolute rather than a default with opt-outs, which is the difference between a convention and a gate. The rewrite is covered by a new grouping-matrix test over all eleven `TimeGrouping` values — the previous suite exercised only the monthly path, and the matrix immediately caught that `generate_series($1, $2)` is ambiguous across the `int`/`bigint`/`numeric` overloads once the bounds stop being literals ([Issue #179](https://github.com/aellington89/finance-stack/issues/179)).
- The audit's own checklist is executable. `tests/integration/actions/validation-contract.test.ts` drives every mutating action with an empty payload and with `1.5` / `Infinity` / `2147483648` in each ID field, asserting the result is a rejection carrying authored text — no SQLSTATE, no `invalid input syntax`, no drizzle `Failed query` preamble — and, via a `console.error` spy, that the rejection happened *before* the database was reached rather than being tidied up by `actionFailure()` afterwards. It keeps itself honest in both directions: the registry is asserted equal to the action modules' actual exports **and** to the table parsed out of the new [docs/input-validation.md](docs/input-validation.md), so a nineteenth action fails CI until it is covered and documented. That table is the issue's first acceptance criterion in a form that cannot rot ([Issue #179](https://github.com/aellington89/finance-stack/issues/179)).

- Dependency and image vulnerability sweep, taking `npm audit --omit=dev` from 19 findings to zero. The critical pair was in the auth stack shipped last cycle: `next-auth` 5.0.0-beta.31 / `@auth/core` could **fail open** — a configuration error populated the auth object rather than rejecting the request — and did not bind OAuth `state`/`nonce`/PKCE cookies to the provider that issued them (fixed by 5.0.0-beta.32). Also patched **SQL injection via improperly escaped SQL identifiers** in `drizzle-orm` <0.45.2, and HTTP request smuggling in `next` rewrites (16.1.6 → 16.2.12). Next vendors `postcss` 8.4.31 (path traversal / arbitrary file read) and `sharp` 0.34.5 (four libvips CVEs) with no fixed Next release available, so both are lifted via `overrides` in `app/package.json`. The `shadcn` CLI moved from `dependencies` to `devDependencies`, where it belonged — it is a scaffolding tool, imported by nothing at runtime ([Issue #131](https://github.com/aellington89/finance-stack/issues/131)).
- The production image no longer ships a package manager. The runner stage deletes `npm`, `npx`, `yarn` and `corepack` — the Next.js standalone server runs `node server.js` and never resolves or installs a package at runtime, so they were pure attack surface, handing anyone who gained execution in the container a way to fetch and run more code. They also carried their own vendored dependencies: npm's bundled `tar`, `sigstore`, `brace-expansion` and `picomatch` accounted for 1 CRITICAL and 5 HIGH findings in the new image scan — every finding it reported — none of which any application-level dependency bump could have cleared. The `migrate` stage keeps npm, since it runs `npx drizzle-kit` ([Issue #131](https://github.com/aellington89/finance-stack/issues/131)).
- All GitHub Actions across the three workflows are now pinned to full commit SHAs rather than mutable tags, with the version recorded in a trailing comment that Dependabot maintains. This is a direct response to the March 2026 compromise in which an attacker force-pushed credential-stealing malware over `aquasecurity/trivy-action`'s existing version tags — the same action this repo's new image scan depends on ([Issue #131](https://github.com/aellington89/finance-stack/issues/131)).

- Postgres surface-area lockdown: the Postgres (`5433`) and Metabase (`3000`) host ports are now bound to `127.0.0.1` instead of `0.0.0.0`, and the three long-running services no longer connect as the `postgres` superuser. Each authenticates as its own least-privilege role — `finance_app` (full DML on the core tables, **`SELECT`-only on `users`**, no DDL), `finance_importer` (append-only on `transactions` plus lookup reads, no `UPDATE`/`DELETE`), and `finance_metabase` (`SELECT` on the three views, no base-table access at all). None can create, alter, drop, or truncate a table, create roles or databases, or reach the `drizzle` migration ledger; tables stay owned by `POSTGRES_USER`. The superuser is retained only for the maintenance jobs that need DDL or cluster-wide reads (`migrate`, `init-script`, `pg-backup`). Roles and grants are created and re-applied idempotently by the `migrate` service on every `docker compose up` (`init-db/roles/`), so existing volumes are upgraded with no manual SQL, and the grant files revoke before granting so a hand-widened privilege converges back. A new CI "role privilege gate" (`scripts/verify-db-roles.sh`) asserts the full matrix against the catalog and then connects as each role to confirm permitted statements succeed and forbidden ones are refused. Documented in [docs/database.md](docs/database.md#roles--privileges) ([Issue #130](https://github.com/aellington89/finance-stack/issues/130)).
- All application pages and every server action now reject unauthenticated requests, enforced in three layers: the Next 16 proxy (`app/proxy.ts`) redirects to `/login`, the `(app)` layout re-verifies the session server-side, and `requireActionUser()` gates each of the 18 server actions individually. Only the landing page, `/login`, `/api/auth/*`, and `/api/health` (Docker healthcheck + release smoke test) remain public ([Issue #120](https://github.com/aellington89/finance-stack/issues/120)).

- CI "seed reference gate" (`npm run check:seed-references`) that verifies the `SEED_REFERENCES` names in code match the `INSERT` rows in `init-db/seeds/shared-lookups.sql`, catching code-side seed drift at build time ([Issue #155](https://github.com/aellington89/finance-stack/issues/155)).
